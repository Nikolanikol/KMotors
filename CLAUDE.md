# CLAUDE.md

Инструкции для Claude Code в этом репозитории.

Разборы инцидентов вынесены в [docs/postmortems.md](docs/postmortems.md), отложенные
вопросы — в [docs/open-questions.md](docs/open-questions.md). Здесь только то, что нужно

## Что это

Full-stack e-commerce на kmotors.shop (бренд в интерфейсе — K-Axis, мягкий ребрендинг,
домен прежний; логотип и палитра — Axis, бронза, см. «Бренд»). Три каталога: подержанные
корейские авто (источник Encar), лоты автоаукционов K Car, Lotte и SK и оригинальные
запчасти Hyundai/Kia/Genesis. Свой AI
SEO-пайплайн, оплата через PayPal, операции через Telegram. Полный список фич и
переменных окружения — README.md.

## Проверка — ОБЯЗАТЕЛЬНА перед тем, как считать задачу сделанной

Сборка ошибок НЕ ловит: в `next.config.ts` стоят `eslint.ignoreDuringBuilds: true` и
`typescript.ignoreBuildErrors: true`. Прошедшая сборка не доказывает ничего. Всегда:

```bash
npm run lint
npx tsc --noEmit
```

Тестов в проекте нет — не рассчитывать на `npm test`.

### Застрял — сообщи сразу, не молчи

lint + tsc обязательны всегда. Всё остальное (браузерная проверка, дев-сервер, скриншоты,
скрипты, внешние API) — если инструмент виснет, отваливается по таймауту или требует
обходных путей, ОСТАНОВИСЬ после ВТОРОЙ неудачной попытки и напиши пользователю: что не
работает, что уже сделано, какие есть варианты. Не уходить в молчаливый цикл обходных
решений — это сжигает время и деньги, а пользователь узнаёт постфактум.

Типовые случаи: панель браузера скрыта (`document.visibilityState === "hidden"` →
скриншоты чёрные; проверять через DOM/read_page или попросить открыть панель), дев-сервер
не поднимается, Encar/Supabase не отвечают.

Правило простое: сама работа важнее её демонстрации. Код готов и проверен через lint/tsc —
доложить об этом и о проблеме с проверкой, дальше решает пользователь.

### Сначала самый короткий путь, а не самый автоматизированный

Перед тем как городить обвязку, спросить себя: как получить это быстрее всего? Часто
ответ — одна команда или готовый интерфейс, а не скрипт.

Смотрим данные в базе — Supabase Dashboard → SQL Editor, один `SELECT`. Не скрипт на
tsx, не curl к PostgREST с подстановкой ключей из `.env`. Разовый вопрос вроде «что
лежит в таблице» вообще не требует кода.

Упёрлись в права — НЕ подбирать обходы (`NODE_PATH`, другой рантайм, временный скрипт в
обход `deny`). Права закрыты намеренно, обход их обесценивает. Сказать пользователю, что
нужно и каким одним действием он это достанет сам.

Живой случай (30.07.2026): чтобы прочитать одну таблицу, ушли скрипт на tsx, попытка
править `.claude/settings.json`, curl к PostgREST — четыре отказа подряд и три круга
разговора о правах, при том что ответ лежал в одном запросе в SQL Editor. Три ветвления
подряд на задаче, которая на вид требует одного шага, — сигнал остановиться и
переспросить, а не изобретать четвёртый путь.

## Деплой и прод — ЧИТАТЬ ПЕРВЫМ

- Каждый push в `main` запускает автоматический редеплой прода (Coolify на VPS). `git push`
  в main — это действие «выкатить», а не «сохранить».
- Supabase развёрнут на том же VPS и является ЖИВОЙ ПРОДАКШЕН-БАЗОЙ. `.env` в репозитории
  смотрит на неё. Любой SQL, любой скрипт с данными, любая команда supabase CLI бьёт прямо
  в прод. Отдельной staging-базы нет.
- Coolify на VPS — единственный живой прод. `vercel.json` остаётся ТОЛЬКО ради headers,
  `netlify.toml` — мёртвый зеркальный конфиг, `output: 'standalone'` для Docker-сборки.
  Строка «Vercel primary» жила в этом файле до 07.2026 и стоила месяца молчащего блога
  ([постмортем](docs/postmortems.md)) — не восстанавливать.
- ⚠️ **Провал сборки НЕ роняет прод — и потому не виден.** Coolify оставляет жить прежний
  контейнер (в логе «Deployment failed. Removing the new version of your application»),
  так что работающий сайт НЕ доказывает, что деплой прошёл. После push проверять URL,
  которого в прежней сборке не было, а не главную. Так деплой простоял двое суток
  ([постмортем](docs/postmortems.md)).
- ⚠️ **`npm i -g npm@11` в Dockerfile — не украшение.** `node:20-alpine` несёт npm 10.8.2,
  а лок генерится локальным npm 11, и мажоры по-разному пишут в лок ОПЦИОНАЛЬНЫЕ
  peer-зависимости (`vite` → `esbuild`): что npm 11 опускает, того npm 10 требует, и
  `npm ci` падает с EUSAGE. Не снимать пин и не менять базовый образ, не сверив, какой
  npm внутри. lint и tsc этот класс поломок не ловят вообще.

## Жёсткие правила

### Работа с репозиторием

- НИКОГДА не делать `git push` — ни в main, ни в любую ветку — без явного подтверждения
  пользователя в текущей сессии. Закоммитить локально, затем остановиться и доложить.
- Вся работа идёт в feature-ветках. Не коммитить прямо в main.
- Навигация по коду: использовать Serena (`find_symbol`, `find_referencing_symbols` и
  т.д.) вместо Grep/Read. Grep — только если Serena недоступна.

### Данные и база

- Не запускать скрипты из `scripts/` или `sql/` без явного подтверждения — они бьют в
  продакшен-Supabase. Запускаются как `npx tsx --env-file=.env scripts/x.ts`, большинство
  резюмируемые/идемпотентные (логи прогресса вроде `scripts/.image-migration.log`); сперва
  прочитать шапку скрипта — там переменные (LIMIT, CONCURRENCY, DELAY_MS).
- Не менять схему БД, RLS-политики и не выполнять разрушительный SQL без явного
  подтверждения.
- `parts_staging` закрыта для кода приложения — это буфер загрузки. Приложение читает
  `parts_products`. ⚠️ Правило В СИЛЕ, но с 22.09.2026 обсуждается: в буфере 92 625
  артикулов, НИ ОДНОГО из которых нет в боевом каталоге. Замеры, три вопроса к закрытию
  и предложенный порядок — в [open-questions](docs/open-questions.md); решение не
  принято, работа не начата.
- Не расширять `parts_fitment` / `parts_vehicle_models` (легаси). Вся новая работа по
  совместимости — в `part_vehicles` + `vehicles`.
- Любой `.range()`/`.limit()` по неуникальному ключу обязан иметь вторым ключом
  `.order("id")` — иначе строки пропадают между страницами
  ([постмортем](docs/postmortems.md)).

### Цены и курсы

- **Запчасти:** хранятся в KRW, показываются в USD через `src/lib/pricing.ts` (`formatUsd`,
  `krwToDisplayUsd`). Не форматировать и не конвертировать цены на месте.
- ⚠️ **«На месте» — это в том числе своя `formatUsd` рядом с импортом настоящей.**
  `FavoritesClient` до 23.08.2026 объявлял локальную функцию с формулой
  `Math.ceil(krw * rate * 1.23)`, затенявшую импорт: она не знала ни про тиеры маржи, ни
  про фикс-надбавку, ни про буфер оплаты, и избранное показывало цены НИЖЕ каталога — на
  6% у дорогих позиций и до 40% у дешёвых. Наценка живёт только в `pricing.ts` и
  настраивается через `NEXT_PUBLIC_PARTS_*` в окружении; множитель в коде страницы —
  всегда ошибка.
- **Авто:** другая модель, `pricing.ts` НЕ применяется. Источник правды —
  `src/lib/carPricing.ts`: цена Encar (만원 × 10 000) ПЛЮС стояночный сбор
  (`NEXT_PUBLIC_CAR_STORAGE_FEE_KRW`, фикс на любую машину). Главная цена в карточке —
  воны; ₽ (ru) / $ (остальные языки) идут ниже как справка.
- ⚠️ **Сбор входит в цену НА ВСЕХ УРОВНЯХ, включая воны** (решение владельца 27.08.2026).
  То есть воны на карточке — уже НЕ цена объявления Encar. Отсюда неочевидные следствия:
  та же сумма обязана стоять в JSON-LD `Offer` (priceCurrency KRW), в цене сниппета
  Google, в перечёркнутой цене проданной машины, в подписи телеграм-постинга и в рассылке
  подписок. Разъедутся — клиент придёт из канала на цену выше, чем ему обещали.
- Подпись «Дилерский стояночный сбор включён в цену» стоит у КАЖДОГО блока цены:
  карточка каталога, сайдбар и мобильная плашка детальной. Ключ
  `common:car.storageFeeIncluded`, заполнен во всех пяти локалях. ⚠️ Мобильная
  плашка в `catalog/[id]/page.tsx` — СЕРВЕРНАЯ и инстанса i18next не имеет, поэтому
  текст там продублирован записью `STORAGE_FEE_LABEL` рядом с `BUY_PRICE_LABEL` и
  `WON_LABEL`. Меняешь формулировку в словаре — меняй и там, иначе локали разъедутся
  между блоками одной страницы.
- ⚠️ **Исключение ровно одно: калькулятор растаможки** (`priceKRW` в `catalog/[id]`).
  База таможни — стоимость сделки, наш сбор в неё не входит. Это НЕ пропущенное место,
  там стоит комментарий; не «приводить к carPriceKrw».
- ⚠️ **Курс для авто берётся у Кукмин-банка**, `src/lib/kbFx.ts` (`getCarRates`), колонка
  `송금 받으실 때` — телеграфный ПОКУПНОЙ: именно по нему банк меняет входящий перевод
  клиента на воны, то есть по нему считается инвойс. Рыночный курс всегда выгоднее
  банковского (замер 27.08.2026: +1.51% USD, +1.24% RUB), и раньше витрина обещала
  цену, по которой сделка не проходит. Рубль тоже от KB. Запчасти остаются на
  `getCurrencyRates` — у них буфер оплаты уже зашит в `pricing.ts`.
- ⚠️ **KB — это чужая HTML-страница без API, поэтому парсер обязан деградировать**, как
  вызовы Encar: не ответила / сменила разметку / отдала бессмыслицу → рыночный курс, и
  падение ЛОГИРУЕТСЯ. Числа проверяются на правдоподобие (вон за доллар 800–3000, за
  рубль 5–60): страница может отдать 200 с переставленными колонками. Колонок в строке
  шесть, брать третью — базовый курс `매매기준율` и курс наличных к переводу отношения
  не имеют.
- ⚠️ **Строку/число цены Encar трактовать ОДИНАКОВО — всегда 만원.** Прежний
  `convertNumber` множил строку на 1000, а число на 10000, и это стоило двух живых
  дефектов: в избранном (цена хранится как `String(car.Price)`) цена показывалась в
  10 раз ниже, а на странице проданной машины `convertNumber(String(priceKrw))` — в
  1000 раз выше. Нормализация теперь одна, в `encarToKrw`.
- **Модельные страницы — третья, отдельная модель цены.** Бейдж «цена под ключ» на
  `[lang]/models/[slug]` берётся из РУЧНЫХ диапазонов `priceFrom`/`priceTo` в
  `src/data/model-pages.ts` (тысячи рублей, с растаможкой) — это не цена Encar. Для
  нерусских локалей он переводится в доллары по `rubToUsd` из `getCurrencyRates` и
  округляется до $500: вилка «от и до» не заслуживает точности до доллара.
  ⚠️ До 27.08.2026 там стоял множитель `10.9` — курс 91.74 ₽/$, зашитый числом. ЦБ к
  тому дню давал 84.28, и англоязычная витрина обещала на 8.9% дешевле, чем русская
  (на GV80 — минус $9 649 по верхней границе). Сами рублёвые вилки заводятся руками и
  на актуальность никем не проверяются — за ними следит владелец.
- ⚠️ **`rubToUsd` берётся из ТОГО ЖЕ ответа ЦБ, что и KRW→RUB.** ЦБ одним запросом
  отдаёт все валюты, поэтому второго похода в сеть у модуля нет. Не заводить под это
  отдельный источник.
- Никогда не зашивать курс константой.
- Источники курсов РАЗНЫЕ и независимые: рубль — ЦБ РФ, доллар — frankfurter. Не сводить к
  одному источнику, не проверив, что он отдаёт ОБЕ валюты; frankfurter не отдаёт RUB
  вообще. `?? FALLBACK` на внешнем курсе — это не подстраховка, а место, где расхождение
  становится невидимым; падение на фолбэк должно логироваться
  ([постмортем](docs/postmortems.md)).
- На любом маршруте, который рендерит ЦЕНУ, `revalidate` не выше 86400: курс запекается в
  HTML в момент рендера, и если страница не перерендеривается, кеш курса опросить некому.
- ⚠️ **Курс запрашивает ТОЛЬКО сервер, через `getCurrencyRates()`.** Клиентские компоненты
  получают его пропсом сверху и своих запросов не делают. До 23.08.2026 три места ходили
  за курсом из браузера мимо этого модуля — `CheckoutClient`, `account/CartTab` (прямо в
  `api.frankfurter.dev`) и `FavoritesClient` (через `/api/exchange-rate`), — каждое со
  своей зашитой константой и `.catch(() => {})`. Константы протухли: `0.00066` («June
  2026») против реальных `0.00072`, то есть минус 8% к цене, и узнать о падении на фолбэк
  было НЕОТКУДА — ошибка глушилась молча.
- Курс раздаёт в том числе `[lang]/layout` — пропсом в `Header` ради корзины в шапке
  (23.08.2026). Это единственный сетевой вызов на пути всего сайта, и он допустим ровно
  потому, что обе выборки внутри идут с `next: { revalidate: 86400 }`: на запрос это
  чтение из кеша данных, а не поход наружу. Не путать с историей `AuthProvider`, откуда
  убрали `supabase.auth.getUser()` — тот ходил по сети НА КАЖДЫЙ рендер, без кеша.
- ⚠️ **Сумму заказа сервер считает по СВОЕМУ курсу, поле из тела запроса игнорируется.**
  `/api/parts/checkout` принимал `krwToUsd` от браузера и писал получившийся `total_usd`
  в `orders`, откуда его брал PayPal как «our authoritative amount». Проверка стояла одна
  (`0 < r <= 0.01`), занизить курс почти до нуля было можно. Клиентский курс существует
  исключительно для показа цен в интерфейсе.

### Изображения

Никогда не читать `image_url` напрямую — только через `src/lib/partImage.ts`
(`resolvePartImage` / `withCleanImage`; предпочитает `image_storage_url`).

### SEO

- Canonical и hreflang всегда идут через `makeAlternates(lang, path)` (`src/lib/seo.ts`).
  `trailingSlash` = false, поэтому путь `"/"` даёт URL с 308-редиректом, и Google
  отбрасывает такой тег — главная передаёт `""`. То же правило в
  `src/app/sitemap-main.xml/route.ts` (`buildUrl`) и во внутренних ссылках на языковой
  корень.
- SEO-пайплайн никогда не трогает живые данные до гейта одобрения в Telegram — этот
  инвариант не менять.
- `public/llms.txt` (23.08.2026) — манифест сайта для ИИ-ассистентов по llmstxt.org:
  markdown, H1 первой строкой, разделы ссылками. Отдаётся статикой, языковой редирект
  его не трогает — `isExcluded` в `middleware.ts` пропускает пути с расширением.
  Это КУРИРУЕМЫЙ вручную документ, а не генерируемый: правишь разделы сайта — правь и
  его. Ценность файла не в списке ссылок, а в блоке оговорок, где сказано то, что
  ассистент иначе переврёт: цена авто в вонах (рубли и доллары справочные), «продана»
  на карточке — норма, а не ошибка, расчёты калькулятора — оценка. Ссылки в файле
  проверять запросом: `/en/models` попал туда по ошибке и давал 404, потому что
  страницы-списка моделей в проекте нет, есть только `/models/[slug]`.

### og-карточки соцсетей (сведено 12.08.2026)

Карточки — ГОТОВЫЕ JPEG в `public/og/<раздел>-<язык>.jpg`, маршруты (`opengraph-image.tsx`)
читают их с диска. Собирает `npm run build:og` из скриншотов в `assets/og-src/`; композиция
и тексты — `src/lib/ogCard.tsx`. До 12.08.2026 на 13 маршрутах стоял
`preview/preview.png` — скриншот старой оранжевой темы с кнопками «Add to Cart» /
«Buy Now», которых на сайте нет.

**Поменяли текст карточки или исходник — перегенерировать и закоммитить JPEG.** Иначе код
и артефакт разъедутся: маршрут продолжит отдавать старую картинку.

- ⚠️ **Собираются заранее, а не в рантайме, по арифметике.** `ImageResponse` умеет отдавать
  только PNG, а PNG с фотографией весит 740–970 КБ при лимите превью у WhatsApp ~300 КБ —
  карточка не показалась бы вовсе. Тот же кадр в JPEG q82 — 40–50 КБ. `sharp` жмёт только
  в сборщике и в `package.json` НЕ добавлен: он приходит транзитивно с Next, а прод от него
  не зависит, он отдаёт готовые файлы.
- ⚠️ **Скриншот кладётся КРОПОМ, а не ужимается целиком.** Уменьшенный до 1200×630 снимок
  страницы — это и был `preview.png`: в превью мессенджера его режут ещё втрое, весь
  интерфейс превращается в кашу. Берётся кусок с полутора карточками в масштабе, близком к
  натуральному. Кропы в манифесте `scripts/build-og-cards.tsx` заданы в пикселях исходника
  под соотношение панели (604×506 ≈ 1.194), иначе sharp досрезает.
- ⚠️ **Имена JSX-директив (`@jsx*`) НЕЛЬЗЯ писать текстом в комментариях `ogCard.tsx`.**
  esbuild ищет их в ЛЮБОМ комментарии файла и берёт СЛЕДУЮЩЕЕ СЛОВО как источник импорта:
  фраза «директивы <имя> сверху» дала попытку загрузить `сверху/jsx-runtime` и падение

### Интерфейс: интерактивность, стиль, удобство — ОБЯЗАТЕЛЬНО (05.10.2026)

Требование владельца: любой экран, меню, модалка или форма отрисовываются сразу по
трём требованиям — интерактивность, стиль бренда, удобство. «Функционально работает»
задачу НЕ закрывает. Повод: меню профиля и окно входа ушли в прод без курсора и без
подсветки при наведении, а кабинет и `/auth` — в старой светлой теме с синим `#002C5F`.

Перед тем как считать UI готовым, пройти список:

- **Курсор.** Всё нажимаемое — `pointer`, отключённое — `not-allowed`, занятое —
  `wait`. Для кнопок это делает глобальное правило в `globals.css` (`@layer base`):
  ⚠️ Tailwind v4 сбросил курсор `<button>` в `default`, в v3 был pointer. Правило не
  удалять; кликабельный `<div>` получает `role="button"` (и тогда курсор тоже от него).
- **Наведение.** У КАЖДОГО интерактивного элемента видимая смена состояния: фон
  (`hover:bg-white/[0.06]` на тёмном), цвет текста или яркость заливки
  (`hover:brightness-115` на бронзе). Только смена цвета текста на сером пункте меню
  почти не видна — нужен фон.
- ⚠️ **Цвет, который меняется на hover, задаётся КЛАССОМ, а не `style={{ color }}`.**
  Инлайн-стиль перебивает `hover:text-*`, и подсветка молча не работает — именно так
  вышли пункты меню профиля.
- **Фокус с клавиатуры.** `focus-visible:ring-2 focus-visible:ring-[rgba(182,119,73,0.6)]`
  на кнопках и пунктах меню; `outline-none` без замены кольцом не ставить.
- **Модалки и выпадашки** отрываются от чёрной страницы многослойной тенью, а не одной
  `shadow-2xl` (на `#0A0A0A` она не видна): ближняя + дальняя + бронзовое свечение,
  образец — `Auth/AuthModal.tsx`. Фон — `--axis-charcoal`, поля внутри — `--axis-graphite`.
- **Только токены бренда.** Тёмные фоны `--axis-black/charcoal/graphite`, текст
  `--axis-white/silver/gray`, акцент — бронза по правилу двух токенов (раздел ниже).
  Светлые фоны, `text-gray-*` под светлую тему и синий `#002C5F` — следы старого
  дизайна; встретил на странице, которую трогаешь, — переводить на токены.
- **Удобство.** Деструктивное (выйти, удалить) отделено и при наведении краснеет;
  статусы читаются на тёмном (`bg-<цвет>-500/10 text-<цвет>-300`); поля `<select>` и
  автозаполнение — `[color-scheme:dark]`, иначе браузер рисует белый список.
- **Отклик на каждый клик, ведущий на другую страницу.** Иначе не понять, зависла
  страница или клик не прошёл — особенно на аукционах, где сервер думает секунды.
  Механизм ОДИН на весь сайт — `src/components/NavigationStatus.tsx` (в `RootShell`):
  бронзовая полоса сверху, пульс нажатого элемента (`data-nav-target`) и приглушение
  блоков с `data-nav-dim`, состояние — `<html data-nav="busy">`. Ссылки и отправку
  форм он ловит сам. Что нужно делать руками:
  - `router.push` из обработчика — звать рядом `navStart(href)` из `src/lib/navStatus.ts`,
    с ПОЛНЫМ адресом: совпадёт с текущим — перехода не будет, и полоса не запустится;
  - GET-форма фильтра — атрибут `data-nav-form`: отправка уходит клиентской
    навигацией вместо перезагрузки страницы;
  - блок результатов — `data-nav-dim`, чтобы старая выдача не выглядела новой;
  - ссылка, открывающая панель вместо перехода, — `data-nav-ignore`.
  ⚠️ `defaultPrevented` у клика по ссылке НЕ проверять: `<Link>` сам зовёт
  `preventDefault` ради клиентской навигации, и проверка отсекает ВСЕ ссылки сайта.
  ⚠️ `popstate` не ловить: Next меняет адрес раньше слушателя, полоса зависала.
  Пакет `next-nprogress-bar` остался в `package.json`, но не используется: прежняя
  полоса была 3px в красном `#BB162B` и формы не видела вовсе.
- **Проверка — глазами в браузере**, наведением на каждый элемент, на десктопе и на
  мобильной ширине. lint и tsc этот класс дефектов не ловят вообще.

#### Словарь `common` разрезан по маршрутам (22.08.2026)

Ресурсы i18next уезжают в RSC-payload КАЖДОЙ страницы, поэтому объём словаря — это вес
каждой страницы сайта. Три раздела `common` занимают 65% файла (`parts` 36%, `buy` 16%,
`tracking` 13%), а нужны ровно своим маршрутам, поэтому они вынесены из глобального
набора: `[lang]/layout` раздаёт `common` БЕЗ них, страницы догружают свой раздел через
`<SectionDictionary lang={lang} sections={["parts"]} />`. Список — `ROUTE_SECTIONS` в
`src/lib/loadLocale.ts`. На главной было 33 KB словаря против 8 KB реально нужного.

Механизм тот же, что у `cars` (`CarsDictionary`) и `customs` (`CustomsDictionary`), и по
той же причине живёт на СТРАНИЦЕ, а не в layout: layout под `[lang]` при клиентской
навигации не перерисовывается, поэтому переход с главной на `/parts` не донёс бы словарь.

- ⚠️ **Раздел из `ROUTE_SECTIONS` обязан быть подключён на КАЖДОЙ своей странице.**
  Забыли — страница покажет клиенту сырые ключи вместо текста, и этого не поймает ни
  `lint`, ни `tsc`, ни сборка: для них это валидный вызов `t()` с несуществующим ключом.
  Проверять только живым запросом. Текущие потребители `parts` — `[lang]/parts/page`,
  `[lang]/parts/[slug]`, `[lang]/parts/category/[slug]`, `[lang]/fitment/[brand]/[slug]`,
  `[lang]/cart`; `buy` — `[lang]/buy`; `tracking` — `[lang]/tracking`. Добавляя маршрут,
  который рендерит компоненты из `src/app/parts/sections/`, класть туда же
  `<SectionDictionary/>`.
- ⚠️ **Прежде чем выносить новый раздел, проверить ДИНАМИЧЕСКИЕ ключи.** Header зовёт
  навигацию как `t(link.labelKey)`, где `labelKey` лежит в массиве ссылок — поиск по
  `t("nav.` таких мест НЕ находит. Вынос `nav` дал бы сырые ключи в шапке всего сайта.
  По этой причине `nav`, `footer`, `contact`, `home`, `cta` остаются глобальными.
- ⚠️ **`SectionDictionaryClient` НЕ повторяет приём `CarsDictionaryClient` с проверкой
  `hasResourceBundle`.** Тот проверяет наличие неймспейса ЦЕЛИКОМ, что верно для `cars` и
  `customs` (свои неймспейсы), но для разделов внутри `common` вернуло бы `true` всегда —
  `common` кладёт layout, — и разделы не добавились бы никогда. Отсюда
  `addResourceBundle(lng, ns, dict, true, false)`: deep-merge без перезаписи.
- Регистрация идёт ВО ВРЕМЯ рендера, а не в `useEffect`, и компонент ставится ПЕРВЫМ в
  разметке страницы. Иначе SSR отдаст в HTML сырые ключи, а первый клиентский рендер их
  заменит и сломает гидрацию.
- Проверка после правок словаря — запросом, а не сборкой. Клиентскую навигацию видно в
  RSC-ответе: `curl -H "RSC: 1" https://.../ru/parts` обязан содержать строки раздела, а
  тот же запрос к `/ru` — не содержать.

#### Модельные страницы: ka/ar падают на АНГЛИЙСКИЙ (27.08.2026)

Тексты в `src/data/model-pages.ts` заведены только для `ru` и `en`, а страница
рендерится на всех четырёх языках. Прежний `content[lang] ?? content.ru` отдавал

Теперь `lang === "ru" ? content.ru : content.en` — тот же приём, что у калькулятора
с `fallbackLng: "en"`. Появятся переводы ka/ar — менять здесь, а не в фолбэке.

`AuthProvider` стоял в `[lang]/layout` и тянул клиент Supabase (242 KB распакованных,
62 KB по сети) в браузер на КАЖДОЙ странице сайта, при том что `useAuth()` не вызывался
ни в одном файле проекта — контекст никто не читал. Вместе с ним ушёл серверный
`supabase.auth.getUser()`, стоявший там же ради пропса `initialUser`: поход по сети к
Supabase перед отрисовкой каталога, запчастей и блога.

Авторизация работает по-прежнему: `/auth`, `/account` и `/checkout` держат собственные
клиенты (`AuthForm.tsx`, `account/*Tab.tsx`, `ProfileForm.tsx`), сессию обновляет
`middleware.ts`. Понадобится общий контекст пользователя — подключать его в layout ТЕХ
сегментов, где он нужен, а не в `[lang]/layout`: этот лежит на пути всего сайта.

Замер главной до/после (прод, по сети): JS 406 → 343 KB, из них 62 KB — ушедший Supabase.

### Каталог авто (на данных Encar)

Вход: `/[lang]/catalog` (листинг) и `/[lang]/catalog/[id]` (карточка). Данные тянутся из
`api.encar.com` на каждый запрос через `src/lib/vehicle.ts` (`fetchVehicleData`);
локальной копии данных о машинах нет.

**Листинг деградирует, а не падает.** `getCars` возвращает `{ data, count, failed }` и
никогда не реджектится; `CarsRow` рисует три разных состояния — машины, «ничего не
найдено» (пустой результат) и «временно недоступно» (`failed: true`) — во всех четырёх
локалях. 404 от Encar означает кривой запрос (например мусор в `?action=`), а не аварию:
он ложится в пустое состояние, не тратя второй поход через прокси.
`src/app/[lang]/catalog/error.tsx` — сегментная граница ошибок, чтобы неожиданный throw
сохранил layout, а не проваливался в корневой `app/error.tsx`.

`page.tsx` и `CarsRow` обязаны звать `getCars` с ИДЕНТИЧНЫМИ аргументами — тот же запрос,
тот же `pageSize`, тот же offset (`(page-1)*pageSize`). JSON-LD `ItemList` должен описывать
список, который реально видит посетитель, а совпадение аргументов позволяет Next схлопнуть
два вызова в один запрос к Encar.

#### Фильтр каталога — шесть уровней дерева Encar (27.08.2026)

`src/components/Catalog/Filter/`. Марка берётся из статичного `FilterData.tsx`
(19 брендов), остальные пять уровней — живьём из `iNav` через `fetchNav(query, depth)`:
2 모델그룹 «Модель» → 3 모델 «Поколение» → 4 등급필터 «Топливо и привод» →
5 등급 «Модификация» → 6 세부등급 «Комплектация». Глубже шестого ничего нет.

- ⚠️ **Уровни не перепрыгиваются.** Фасеты уровня N Encar отдаёт, только когда в
  запросе выбран N−1. Цепочка выпадашек — форма дерева, а не выбор дизайна.
- ⚠️ **Пункт «Без комплектации» (`NO_TRIM`, строка `(세부등급 없음)`) прятать НЕЛЬЗЯ.**
  Замер на 600 машинах: у 24% там эта строка, ещё у 27% поля нет вовсе — половина
  каталога. Спрятать = сделать половину недостижимой через фильтр. Это данные Encar,
  а не дыра: у новых Genesis всё описание уехало в 등급 (объём, топливо, привод), а
  отдельного уровня оснащения там просто нет.
- ⚠️ **Все пять уровней видны ВСЕГДА, даже когда выбирать нечего** (решение владельца
  27.08.2026). Сперва пустые уровни скрывались — и вёрстка прыгала: цена, пробег и год
  ездили вверх-вниз на каждый выбор, а три новых уровня вели себя не так, как «Модель»
  и «Поколение», которые всегда на месте с `disabled`. Состояний у строки три:
  родитель не выбран, `filter.loading` пока идёт запрос, `filter.noOptions` когда
  Encar вернул пусто. Ховер у `:disabled` погашен намеренно — CSS `:hover`
  срабатывает и на отключённой кнопке, а бронзовая подсветка обещала бы клик,
  которого не будет.
- **Словарь комплектаций живёт в `cars.json` и он ПОСЛОВНЫЙ** —
  `translateGenerationRow` бьёт строку по пробелам. Заполняется английский (он же
  фолбэк для ru/ka/ar по `fallbackLng`), русский — только для описательных корейских
  слов (고급형 «Люкс-версия», 영업용 «Коммерческая»): названия уровней оснащения на
  российском рынке и так пишут латиницей. Проверено на 5 000 машин 16 марок:
  172 разных названия, покрытие 100%. Появится незнакомое слово — снять свежую
  выборку `BadgeDetail` из листинга и дописать недостающие.
- ⚠️ **Стили селектов — классы `.filter-select` / `.filter-menu` в `globals.css`, а НЕ
  правка `src/components/ui/select.tsx`.** Тот же примитив используют каталог
  запчастей (палитра `--pn-*`) и поле телефона. Список Radix рендерится в ПОРТАЛЕ,
  вне разметки фильтра, поэтому достать его потомком нельзя — класс вешается прямо
  на `SelectContent`.
- ⚠️ **У пункта «любой» обязан быть СТРОКОВЫЙ сентинел (`ANY_VALUE`), а не `null`.**
  Radix строку и ждёт, а `null` ломался молча и дорого: обработчик марки делал
  `data.filter(...)[0].title`, на сбросе совпадений нет, `[0]` — `undefined`, и
  ВЕСЬ фильтр уходил в границу ошибок — сбросить марку было нельзя. tsc показывал
  на это место семью ошибками «Type 'null' is not assignable to type 'string'»,
  все семь исчезли вместе с починкой; сборка их не ловит, потому что в
  `next.config.ts` стоит `ignoreBuildErrors`.
- ⚠️ **Сброс верхнего уровня обязан обнулять всю цепочку вниз** (`resetChain`).
  `ModelsRow` чистил только собственное значение, поэтому после смены марки модель,
  поколение и комплектация оставались от ПРЕЖНЕГО бренда. На сбросе запрос
  возвращается к родительскому уровню, а не в `null`: иначе «Показать» уходил бы с
  пустым `action` и кнопка молча ничего не делала.
- Фильтр НЕ восстанавливает выбранное из адреса: после «Показать» `action` из URL
  читается, а цепочка марка → модель → … собирается заново с нуля, и выпадашки
  выглядят пустыми при применённом фильтре. С шестью уровнями заметнее, чем с тремя.
  Отложено, см. [open-questions](docs/open-questions.md).
- ⚠️ **Сырые ключи после правки словаря — почти всегда СТАРАЯ страница, а не баг.**
  Дев-сервер держит сборку, поднятую до правки, а клиентский кеш роутера Next отдаёт
  прежний RSC-пейлоад при возврате на маршрут. Проверять не глазами, а запросом:
  `curl -s localhost:PORT/ru/catalog | grep -c 'filter\.selectEngine'` обязан дать 0.
  Дало 0, а на экране ключи — перезапустить дев-сервер (`npm run dev:clean`).

#### Карточка авто — метаданные

Файл `src/app/[lang]/catalog/[id]/page.tsx`. Три связанных инварианта:

1. `title` и H1 обязаны совпадать. Google берёт H1 как основной источник, переписывая
   заголовок в выдаче; английский H1 под локализованным title провоцирует переписывание.
   Оба несут модель + комплектацию + год + локализованное «из Кореи» в одном порядке слов.
2. Цена в сниппете обязана совпадать с ценой, которую видит посетитель (ru → ₽, остальные
   → $). Порядок: модель → год → гео → цена. `ka` — исключение, там цена перед гео:
   грузинские глифы широкие (Google режет по ширине в пикселях), а гео-слова в целевом
   запросе нет.
3. В JSON-LD `Offer` остаётся `priceCurrency` KRW — оно должно совпадать с главной ценой в
   `CarDetailSidebar`, а не со справочной конвертацией.

Дальше:

- Корейские слова из спецификации (`carShape` «세단 4도어», `transmissionName` «오토»,
  `fuelName` «LPG(일반인 구입)») обязаны проходить через `src/lib/carLabels.ts`. У
  `generateMetadata` нет инстанса i18next (i18n поднимается на запрос), поэтому он читает
  `cars.json` напрямую. Правило: если слово осталось хангылем после подстановки — выкинуть
  всё поле. Пустое поле лучше корейского в сниппете Google.
- `manufacturerEnglishName` приходит склеенным: `ChevroletGMDaewoo`,
  `Renault-KoreaSamsung`, `KG_Mobility_Ssangyong`. Всегда показывать через
  `normalizeBrand()`. Он питает H1, title, description и `brand` в JSON-LD.
- H1 несёт префикс title слово в слово (модель + комплектация + год + локализованное «из
  Кореи»), затем приглушённая подстрока «пробег · коробка». Удлинять хвост можно; менять
  общий префикс — значит ломать инвариант 1.
- Использовать `formatYear()` («2024») в title/H1/description. `formatDate()` возвращает
  формат регистрации Encar «YY.MM» — только для строк спецификации; покупателю вне Кореи
  это читается как шум.
- Суффикс «| K-Axis» из глобального шаблона title подавлен на карточках через
  `title: { absolute }` — экономит ~9 символов из бюджета в ~60.

#### Карточка авто — сознательные компромиссы рендера, НЕ «чинить» как баги

Два блока намеренно исключены из первой отрисовки. Оба измерены и выбраны осознанно;
предложение отрендерить их на сервере — это продуктовое решение, а не отчёт о дефекте.

- Названия опций (`OptionsRow`) лежат в свёрнутых аккордеонах Radix и в серверном HTML их
  НЕТ — есть только счётчики по категориям («Стандартные опции 37, Комфорт 11…»). Encar
  присылает коды («001», «004», …), они резолвятся по словарю из 218 записей в
  `OptionsRow/data.ts`. Свёрнутость + ленивый маунт — это то, что держит первую отрисовку
  дешёвой. Известная цена в SEO: ~37 реальных названий опций на машину не попадают в HTML.
- `RecommendedCars` грузится по скроллу (IntersectionObserver → `/api/recommended`). Боты
  поэтому видят `<h2>` с пустой каруселью и не получают из карточки ни одной внутренней
  ссылки. Принято по той же причине.

Контраст — `DetailInfo` (спецификация + история аварий и владельцев): его ПЕРЕНЕСЛИ на
сервер (`src/lib/vehicleRecord.ts` + `DetailInfoSection.tsx` за Suspense), потому что это
самый уникальный контент карточки. Suspense сохраняет быструю первую отрисовку, а блок всё
равно оказывается в том же HTTP-ответе — вот образец, если что-то из перечисленного выше
когда-нибудь будут переносить на сервер.

#### Карточка авто — картинки

Галерея и лайтбокс — намеренно разные пути: лайтбокс (yet-another-react-lightbox,
`dynamic ssr:false`, свои `LIGHTBOX_WIDTHS` до 1920) не грузит ничего, пока пользователь
его не откроет. Проверено. Размеры для мобильных и превью посчитаны верно, для десктопа —
нет; детали в [docs/open-questions.md](docs/open-questions.md).

#### Проданная машина

Проданная машина = 404 от Encar = `fetchVehicleData` возвращает `null`.

`fetchVehicleData` отличает «продана» (Encar 404 → `null`) от «апстрим лежит» (бросает
`VehicleUpstreamError`). `generateMetadata` ставит `noindex` ТОЛЬКО для случая продажи.
Никогда не схлопывать эти две ветки в `catch(() => null)`
([постмортем](docs/postmortems.md)).

При `data === null` рендерится `SoldCarPage`: снимок из `cars_seen` (фото, характеристики,
перечёркнутая прежняя цена), кнопка подписки deep-link'ом в бота и мессенджеры с готовым
текстом. `notFound()` на этом маршруте остался только для непустого, но кривого ответа.
Раньше в обеих ветках стоял `notFound()`, и весь входящий поисковый трафик на проданные
машины (сотни URL в индексе) попадал в пустую заглушку — при том, что посетитель тут самый
квалифицированный из возможных, он искал конкретную модель.

- ⚠️ `noindex` остаётся. Страница живёт ради людей, уже пришедших из индекса, а не ради
  ранжирования; вернём индексацию — вернутся сотни «дубликатов без канонического» в GSC.
  Выставляется независимо, в `generateMetadata`, и от рендера не зависит.
- Имя собирается ТОЛЬКО из английских полей снимка через `normalizeBrand`. Нет их (снимок
  из бэкфилла) — показывать нейтральный заголовок, а не хангыль.
- Снимка нет вовсе — блок похожих не рендерится, страница деградирует до «объявление
  снято» + подписка + каталог.
- Похожие подбираются в `src/lib/similarCars.ts`: марка + модельная группа + год ±1 + цена
  ±15%, корейскими именами из снимка. Собственный `recommend/{id}` у Encar для этого не
  годится — он привязан к живому объявлению.
- ⚠️ Не восстанавливать хардкод `<meta name="robots" content="index, follow">`, который
  когда-то стоял в `src/app/layout.tsx` ([постмортем](docs/postmortems.md)).

#### cars_seen — снимки машин Encar

Файлы: `src/lib/carsSeen.ts`, `src/lib/carsSync.ts`, `sql/035_cars_seen.sql`.

Encar держит объявление только пока машина продаётся: после продажи
`/v1/readside/vehicle/{id}` отдаёт 404, и от машины не остаётся ничего — ни марки, ни
модели, ни цены. `cars_seen` — наша копия данных, чтобы страницу проданной машины было чем
наполнить и из чего собрать запрос «покажи такие же».

⚠️ **С 02.10.2026 у таблицы ВТОРАЯ роль: она источник сайтмапа каталога** (см. раздел про
сайтмапы). Отсюда третий путь записи и смысл суточного крона — до него новая машина
попадала в таблицу только после того, как кто-то открыл её карточку, а открыть её Google не
мог, пока адреса нет в сайтмапе. Замкнутый круг и держал каталог невидимым.

Пишется тремя путями, все upsert по `encar_id`:

| путь | что делает |
|---|---|
| рендер карточки, через `after()` | богатый снимок из `/v1/readside/vehicle/{id}` |
| задание `cars`, `/api/cars/sync` | обход листинга, по 500 машин в сутки |
| `scripts/backfill-cars-seen.ts` | разовый залив с локальной машины |

Логика обхода у крона и скрипта ОБЩАЯ (`src/lib/carsSync.ts`) — второй копии в скрипте
больше нет, она бы разошлась с боевой при первой правке.

Инварианты:

- ⚠️ Ботов при записи снимков НЕ фильтровать, хотя рука тянется. Снимок нужен ровно тем
  страницам, что получают трафик из поиска, а попасть в поиск страница может только после
  обхода Googlebot'ом — обход и есть тот рендер, который мы записываем. Отфильтруем ботов —
  снимки останутся только у машин, которые кто-то открыл руками, а это малая доля индекса.
  Обратный фильтр (`isbot` в `middleware.ts`) существует для аналитики и сюда не
  переносится.
- `sold_at` ставится ТОЛЬКО на строгий `null` от `fetchVehicleData`. Авария апстрима бросает
  `VehicleUpstreamError` и до этой ветки не доходит; непустой, но кривой ответ продажей
  тоже не считается — иначе сбой парсинга у Encar пометил бы живые машины проданными.
- Единицы: `price_manwon` хранится в 만원, КАК ОТДАЁТ ENCAR, без пересчёта. В воны —
  × 10000, ровно как это делает карточка. Не путать с запчастями, где `price_krw` — это
  настоящие воны.
- Троттлинг в памяти инстанса (1 час) стоит и на записи снимка, и на отметке продажи; ключи
  разведены префиксами `seen:`/`sold:`, иначе снимок съедал бы право отметить ту же машину
  проданной в том же часе. Id, не подходящие под `/^\d{6,10}$/`, отсекаются до похода в
  базу — в `/catalog/[id]` прилетает мусор из индекса и от сканеров.
- Модуль не бросает исключений НИКОГДА: карточка авто важнее снимка. Пока таблицы нет или
  Supabase лежит — только `console.error`.

#### Подписки «пришлём похожие»

Файлы: `src/lib/savedSearches.ts`, `sql/036_saved_searches.sql`.

Человек нажал кнопку на странице проданной машины → бот запоминает запрос → крон раз в
сутки пишет ему, когда подходящее появилось. Смысл в том, что на проданную карточку
приходят именно за тем, чего сейчас НЕТ в наличии.

Бот — существующий KMOTORS_form_bot, тот же `TELEGRAM_BOT_TOKEN`. Его `/start` уже
публичный и обрабатывается ДО гейта `isAdmin`, рядом с разбором `car_<id>`; отдельный бот
разнёс бы клиентский опыт по двум чатам. Метка `sold_<encar_id>` несёт всё нужное, поэтому
ни токенов, ни промежуточного роута создания подписки нет.

Инварианты — все найдены живыми тестами и в коде не видны:

- ⚠️ Новизна определяется по `manage.firstAdvertisedDateTime` из КАРТОЧКИ, а не по
  отсутствию `Id` в `seen_ids` ([постмортем](docs/postmortems.md)).
- Даты Encar отдаёт без зоны, время корейское — разбирать как `+09:00` явно, иначе
  `Date.parse` считает их UTC и сдвигает на 9 часов.
- `FETCH_LIMIT` общий для засева и крона, живёт в `savedSearches.ts`. Разойдутся — и на
  первом прогоне давно висящие объявления уедут человеку как новинки.
- `seen_ids` схлопывается (`compactSeen`), иначе копит дубли: замер на проде дал 111
  записей при 60 уникальных. Оставляем ПОСЛЕДНЕЕ вхождение — срез идёт с конца.
- Названия машин берутся из карточки (`manufacturerEnglishName` / `modelGroupEnglishName` /
  `gradeEnglishName` + `normalizeBrand`), а НЕ из листинга: в листинге только корейские
  ([постмортем](docs/postmortems.md)). Карточка и так запрашивается ради даты подачи,
  второго запроса не нужно.
- `parse_mode` HTML, имена приходят от Encar — экранировать `<` `>` `&`. Кривой тег роняет
  отправку целиком (Telegram отвечает `ok:false`).
- Апстрим не ответил (`failed`) — НЕ трогать ни `seen_ids`, ни `last_sent_at`: авария Encar
  молча съела бы новинки, зачислив их в «виденные» без отправки. По той же причине
  `seen_ids` пополняется только после УДАЧНОЙ отправки.
- Подписку не создаём, если Encar лёг: пустой засев = ложные новинки на первом прогоне.
- Отписка (кнопка `unsub:<id>`) сверяет `chat_id` — `callback_data` приходит от клиента,
  без сверки любой отписал бы чужую подписку по произвольному id. Обрабатывается до гейта
  `isAdmin`, как и `/start`. Массовая отписка — команда `/stop`.
- ⚠️ `SEND_COOLDOWN_MS` обязан быть МЕНЬШЕ периода крона. Сейчас 20 часов при суточном
  расписании, и это не небрежная замена 24 ([постмортем](docs/postmortems.md)).
- Отчёт о каждом прогоне уходит в `TELEGRAM_WORK_CHAT_ID` (`reportToWorkChat`), подписчик
  его не видит НИКОГДА — это отдельная ветка, клиенту пишет `sendToChat` по его
  `chat_id`. Отчёт разводит три состояния, неразличимые снаружи: «разослано», «новинок
  нет» и «к проверке никого» (все неактивны или в кулдауне). Плюс счётчик
  `failedQueries`: авария Encar и пустая выдача — разные вещи.

Настройки (решение владельца): проверка раз в сутки, не чаще одного сообщения в 20 часов
на человека, не больше пяти машин в сообщении. Одинаковые запросы дедуплицируются по
строке `query` — из Encar тянутся один раз и раздаются веером.

### Аукционы K Car, Lotte и SK (09.2026)

Второй источник машин рядом с Encar: лоты корейских автоаукционов. ТРИ площадки в
одних таблицах (`auction_lots`, `auction_results`, `auction_sync_runs`), различаются
колонкой `source`. Витрина публичная — `/[lang]/auction` (K Car, вкладка по умолчанию),
`/[lang]/auction/lotte` и `/[lang]/auction/sk`; служебная — `/admin/auction` с теми же
вкладками.

**Источники разной природы, и это определяет всё остальное:**

| | K Car | Lotte и SK |
|---|---|---|
| откуда | собственный публичный API аукциона | витрина-посредник `dokanmazad.com` |
| модуль | `src/lib/kcar/` | `src/lib/showcase/` |
| история торгов | есть, 12 831 наблюдение | нет и не будет |
| прогноз молотка | считается | невозможен |

⚠️ **Лоты ВСЕХ ТРЁХ площадок приезжают с витрины-посредника** одним обходом; площадка
определяется по хосту картинки (`PROVIDER_BY_IMAGE_HOST` в `scrape.ts`:
`kcarauction.com` → kcar, `imgmk.lotteautoauction.net` → lotte,
`aucmark.skcarrental.com` → sk). Собственный API K Car остался нужен ТОЛЬКО ради
истории прошедших торгов (`auction_results`), на которой стоит прогноз молотка —
у витрины таких данных нет и не будет.

Замер 21.09.2026: один обход 79 страниц, ~6 минут с повторами, 2 315 лотов —
Lotte 1 451, SK 516, K Car 348.

⚠️ **У витрины есть свой Cloudflare, и он отдаёт 525 примерно на каждой тридцатой
странице.** Отсюда повторы в `getHtml` (три попытки, паузы 1.2 и 2.4 с): без них из
шести страниц не отдались две, с ними прошли 78 из 78. Без повторов каждый прогон
молча терял бы по паре страниц, а счётчик «страниц обойдено» выглядел бы нормальным.

#### Дедлайн торгов — 04:00 UTC, и он ВЫЧИСЛЕН

`AUCTION_END_HOUR_UTC` в `src/components/Auction/auctionTime.ts` — 04:00 UTC, то есть
13:00 по Корее. Нигде не объявлен: получен обратным счётом из обратного отсчёта самой
витрины, сходится у SK и K Car.

⚠️ **Отбор активных лотов сравнивает с ним, а НЕ с календарной датой** (`activeFrom()`
в `kcar/query.ts`). Лот с датой «сегодня» проходил бы фильтр до полуночи — двадцать
часов витрина показывала бы машины, которых на аукционе уже нет. Наблюдалось живьём
21.09.2026: сразу после дедлайна площадка вычистила партию Lotte целиком, 1 451 лот за
полчаса.

⚠️ **Та же отсечка обязана стоять у блока похожих лотов** (`getSimilarLots`). Там её не
было, и блок предлагал лоты с ПРОШЕДШИХ торгов: клик вёл на страницу, где витрина
отдаёт 404. Живой случай 21.09.2026 — предлагался `CA20389500` с торгами 7, 11 и 15
сентября. Каталог такие лоты прячет, а похожие брались из той же таблицы запросом мимо
правила.

#### Расписание торгов собирается САМО

Расписания площадки не присылают, и на витрине его нет. Но раздел держит по ОДНОЙ
ближайшей дате торгов на площадку, а лоты исчезают после дедлайна — значит новая партия
появляется в неизвестный момент. Отсюда правило: ходить часто и дёшево, а не редко и по
угадайке (крон раз в 4 часа).

Каждый прогон пишет в `auction_sync_runs` поле `notes.dates` — даты торгов по площадкам.
Через неделю по этой истории видно и ритм торгов, и момент выкладки новой партии; тогда
расписание можно сузить, опираясь на замер, а не на догадку.

#### Цены

- **Всё в вонах, в одной колонке `start_price_krw`.** У Lotte витрина умеет отдавать
  цену в долларах, но это её собственный пересчёт по неизвестному курсу, поэтому в
  запросе списка стоит `?currency=KRW` (замер 12.09.2026: ₩38 784 000 против $28 894,
  курс ≈1342.3). Колонка `price_usd` осталась в схеме пустой и НЕ используется.
- ⚠️ **Цена на витрине — СТАРТОВАЯ, и об этом сказано над списком** (решение владельца
  12.09.2026). Лот уходит в среднем на 14% дороже старта (медиана по 9 651 сделке), а
  сверх того идут сбор аукциона, доставка и растаможка. Оговорка живёт в `shell.tsx`,
  одна на обе вкладки — разъедутся, и вкладки начнут обещать разное.
- `carPricing.ts` здесь НЕ применяется: это третья модель цены после Encar и запчастей.

#### auction_results — наблюдения, а не лоты

- Ключ `(source, external_id, session)`. Непроданный лот возвращается на следующие торги
  с тем же id; ключ без сессии терял 2 922 строки из 11 720 ([постмортем](docs/postmortems.md)).
- ⚠️ **Цена молотка НЕ признак продажи**: площадка ставит туда стартовую и у
  несостоявшихся торгов. Признак — повторное появление лота в более поздней сессии;
  размечает функция `auction_results_refresh_sold()`, вызывается после каждого upsert.
- ⚠️ **Торги идут ДВАЖДЫ в неделю** — вторник (чётные сессии) и четверг (нечётные),
  замерено по 990–997. Четверг вдвое крупнее. Крон обязан брать ДИАПАЗОН сессий: с
  одним номером терялось бы 65% выборки, причём молча — с `ok:true` в логе.

#### Добор деталей (enrich) — источник мёртв

`detail.ts` брал VIN, галерею и лист осмотра со сторонней витрины
(`motors.wasigroupsa.com`) массовым обходом. Механизм МЁРТВ и заменён: детали грузятся
по требованию при открытии лота, через `src/lib/showcase/query.ts`, и работают для всех
трёх площадок.

Историческая справка, она же урок: 12.09.2026 та витрина целиком перешла на Lotte, лотов
K Car там не осталось — полный обход 1401 карточки дал ноль совпадений. Парсер при этом
был исправен, изменились ДАННЫЕ, и прогон отчитался `ok: true, enriched: 0, failed: 0`,
потратив 53 минуты. `failed` считает только неотданные страницы, а «разобрано, но чужая
площадка» не считал никто.

- ⚠️ Перед обходом стоит предпроверка: нет K Car в первых 12 карточках — выход с
  `notes.aborted` за две минуты вместо часа. Счётчики разводят четыре исхода
  (`failed`, `skipped` по площадкам, `unmatched`, `aborted`); до этого 53-минутный
  прогон отчитывался успехом, ничего не собрав.
- ⚠️ **VIN в публичном API аукциона нет** (проверены все 236 полей). Зато есть лист
  осмотра: `JINDAN_EX_LIST` → `defect_parts` со словарём `DEFECT_PARTS`.
- ⚠️ **Миниатюра приходит в СПИСОЧНОМ ответе** (`THUMBNAIL_MOBILE`), а не в доборе, и
  лежит в `thumb_url`. Путь из `external_id` не выводится — в имени файла случайный
  токен, поэтому URL хранится.

#### toLot не имеет права писать null в колонки добора

Поля `vin`, `photos`, `inspection`, `diagram_url` и прочие заполняет только enrich.
Раньше `toLot` подставлял туда `null`, и ЕЖЕДНЕВНЫЙ синк лотов затирал результат
еженедельного добора к следующему утру. Теперь строка без деталей идёт типом
`AuctionLotBase` — БЕЗ этих ключей, — а `sync.ts` пишет двумя upsert'ами: PostgREST
требует одинакового набора ключей внутри одного bulk-запроса.

#### Витрина-посредник: разбор чужой RSC-разметки

- ⚠️ **Половина данных карточки лежит в ОТЛОЖЕННЫХ кусках потока** (`$L97`), которые
  объявляются по всему документу, в том числе после самой карточки. Без их разрешения
  парсер видит только цену, пробег и фото — ни года, ни топлива, ни коробки.
- Название приходит разобранным в пропе `parts`: `["Carnival","THE NEW (D) 2.2 …"]`.
  ⚠️ Там бывает JSON-`null` (комплектации нет) — резка строки по запятой превращала его
  в текст «null» на карточке. И бывают экранированные кавычки (дюйм диска, `20"`), от
  которых остаются слэши.
- Дата окончания торгов приходит пропом таймера `date`, а не текстом: на карточке
  витрина показывает обратный отсчёт.
- Детали лота (37 фото, диаграмма кузова) грузятся ПО ТРЕБОВАНИЮ при открытии, а не
  массовым обходом: 1401 страница с паузой — это час ради карточек, которые никто не
  откроет. Кеш обязателен — иначе каждое обновление бьёт по чужому серверу.
- ⚠️ **В ключе кеша деталей стоит ВЕРСИЯ формы** (`showcase-lot-detail-v6`). Поменяли
  состав `ShowcaseDetail` — поднимите её, иначе кеш час отдаёт объекты прежней формы и
  новые поля выглядят пустыми при исправном парсере.
- ⚠️ Диаграмма состояния кузова — ГОТОВАЯ КАРТИНКА в `accidentImages`, по одной на лот.
  Поле `reports` у лотов витрины пустое (проверено на 33). Следствие: показать можно,
  отфильтровать по состоянию нельзя. У K Car наоборот — панели приходят структурой.

#### ⚠️ «Лот ушёл» и «витрина легла» — РАЗНЫЕ исходы

То же правило, что у `fetchVehicleData` с Encar, и цена ошибки та же. Снаружи оба
случая выглядят как «деталей нет», а значат противоположное: 404 — лот ушёл с торгов и
не вернётся, таймаут или 525 — лот, возможно, жив. Объявить проданным живой лот, пока
витрина лежит, значит соврать клиенту.

`getHtml` отдаёт три исхода (`html` / `gone` / `failed`), `fetchDetail` — `DetailResult`,
`getShowcaseDetail` — `ok` / `gone` / `unavailable`. Страница лота разводит их плашкой:
«Лот ушёл с торгов — скорее всего продан» против «Подробности временно недоступны».

- ⚠️ **404 НЕ ретраится.** Ответ не изменится, а три попытки с паузами — это 3.6 секунды
  ожидания на странице, которая всё равно отрисуется без деталей, плюс два лишних
  запроса к чужому серверу.
- ⚠️ **`gone` кешируется, `failed` — НЕТ.** Первое устойчивый факт, второе временное:
  витрина полежит минуту, а мы час показывали бы «деталей нет» при живом лоте. Отсюда
  бросок исключения на `failed` — оно в кеш не попадает.
- Формулировка «ушёл с торгов», а не «продано», намеренно: 404 означает, что лот исчез
  с витрины, а продали его или сняли — мы не знаем.
- Страница в обоих случаях РАБОТАЕТ: снимок, характеристики и цена старта лежат в нашей
  базе и от витрины не зависят.

#### Интерфейс

- **Компоненты не знают про i18next.** `LotCard`, `LotFilters`, `AuctionTabs` принимают
  подписи пропом: карточка живёт и под `/admin`, где инстанса i18next нет вовсе, и под
  `[lang]`, где он есть только на клиенте, а сама она серверная. Публичная витрина берёт
  строки через `auctionLabels.ts` (читает словарь напрямую, как `carLabels.ts`),
  служебная — через `RU_LOT_LABELS`. Так карточки остались серверными, без JS.
- Раздел `auction` в `ROUTE_SECTIONS`, но `<SectionDictionary/>` ему НЕ нужен —
  клиентских потребителей у ключей нет. `ka`/`ar` раздела не имеют намеренно, тексты
  приходят фолбэком на английский (приём калькулятора).
- ⚠️ **Значения характеристик двуязычны через `specLabel`.** В базе смесь: у K Car
  словарь переводит корейское в РУССКОЕ при загрузке, витрина отдаёт сразу АНГЛИЙСКОЕ.
  До этого русская витрина показывала `Diesel · Manual`, а английская — `Дизель · АКПП`.
  Ключ таблицы — значение из базы, а не корейский оригинал: оригинала в базе нет.
  `pair()` в `kcar/dict.ts` регистрирует ОБА написания ключами к одной паре, поэтому
  таблица годится и как канонизатор — если однажды понадобится фильтр по топливу.
- ⚠️ **Фасет собирается БЕЗ СВОЕГО измерения.** Марки — при `withMaker: false` И
  `withModel: false`; модели — при `withModel: false`, но С фильтром по марке. Иначе
  выпадашка схлопывается до единственного выбранного пункта и сменить его можно лишь
  правкой адреса. Второе условие у марок не менее важно первого: выбранная модель
  схлопнула бы список марок до одной — та же ловушка с другой стороны.
- ⚠️ **Подстановка корейских слов идёт от ДЛИННОГО ключа к короткому.** В `MODEL_TOKENS`
  есть `쿠페` → Coupe, и он превращал `그란쿠페` в `그란Coupe`, после чего длинный ключ не
  совпадал, а слово с остатком хангыля отсеивалось целиком.
- Табы — `<Link>`, а не `useState`: у каждой площадки свой адрес. Тот же приём, что у
  калькулятора растаможки.
- Галерея переиспользована из карточки авто (`Catalog/CarDetail/Carousel`). Для чужих
  CDN у неё есть `imageSource="raw"`: по умолчанию она дописывает к адресам параметры
  Encar с водяным знаком. Загрузчик, игнорирующий ширину, заменён на `unoptimized` —
  иначе на каждую миниатюру уезжал бы полноразмерный кадр.
- Публичная витрина под `noindex` (решение владельца 12.09.2026): лоты живут дни, и
  индексация дала бы сотни 404 в GSC — как было со страницами проданных машин.
- Пункт «Аукцион» в шапке стоит ВНУТРИ того же гейта `isCatalogBlocked`, что и каталог
  авто: это те же корейские машины.
- ⚠️ **`getPremiumIndex` обязан быть НЕбросающим.** Прогноз идёт третьим элементом в
  `Promise.all` на трёх страницах, а `Promise.all` реджектится, если упал ЛЮБОЙ элемент.
  Соседние `getLots` и `getSourceCounts` сбой переживают, поэтому исключение отсюда
  роняло страницу целиком — включая `/[lang]/auction`. Путь до броска короткий:
  `createServerClient` зовёт `createClient` с `!` на переменных окружения, а тот бросает
  СИНХРОННО при пустом ключе. Достаточно потерять переменную в Coolify.
- У сегмента есть свои границы ошибок — `[lang]/auction/error.tsx` и
  `admin/auction/error.tsx`. Ловят не чтения (те закрыты по одному), а рендер на
  неожиданной форме строки и будущие вызовы без try/catch. ⚠️ Проверить их срабатывание
  синтетическим падением НЕ удалось: и dev, и прод отдают страницу Next `__next_error__`
  вместо текста границы, а контрольный опыт не вышел — у запчастей и каталога слои
  чтения тоже деградируют, и до их границ падение не доходит. Компоненты в бандл
  попадают, размещены как у каталога; ловят ли они такое в принципе — неизвестно.

#### Фильтр витрины

Поиск строкой, марка, модель, цена до, год от, пробег до, сортировка.

⚠️ **Состав задан НЕ удобством, а пересечением площадок.** Марка, модель, год, пробег и
цена — единственные поля, которые есть и у своего API K Car, и у витрины-посредника: та
отдаёт ровно одиннадцать полей, столько же, сколько показывает на карточке. Цвет, кузов,
привод, объём, число мест, оценка кузова, повреждённые панели и прогноз премии есть
ТОЛЬКО у K Car — фильтр по ним работал бы на одной вкладке из трёх, и человек при
переключении получал бы другой набор контролов.

- ⚠️ **Смена марки ОБНУЛЯЕТ модель** (тот же `resetChain`, что у фильтра каталога Encar).
  Без этого после перехода Kia → Hyundai в адресе оставалась бы модель прежнего бренда,
  выдача становилась бы пустой, а выпадашка показывала бы значение, которого нет в
  списке.
- Модель видна ВСЕГДА, но отключена, пока не выбрана марка — приём уровней фильтра Encar
  (владелец решил уровни не прятать: вёрстка прыгает на каждый выбор).
- Пороги диапазонов КРУГЛЫЕ (₩5–30 млн, 2015–2022, 50–200 тыс. км), а не снятые с
  распределения: партия лотов меняется дважды в неделю целиком, и ступени под одну
  партию на следующей были бы неверны. Выпадашки, а не ползунки — ползунок требует
  клиентского состояния и дебаунса, а сетка карточек серверная.
- ⚠️ **Числа из адреса ПРОВЕРЯЮТСЯ, а не приводятся** (`num()` в `readParams`).
  `Number("abc")` это `NaN`, и он уходит в PostgREST строкой `"NaN"`: запрос отвечает
  400, а `getLots` показывает «временно недоступно» вместо лотов.
- Разбор адреса НЕ дублируется: служебная витрина берёт `readParams` и `hasFilters` у
  публичной. Раньше обе читали `searchParams` своими руками, и каждый новый фильтр
  пришлось бы заводить дважды — то есть однажды забыть.
- Лот без года не проходит фильтр «год от»: `.gte("year", …)` на `null` даёт false. Это
  верно по смыслу, но заметно — года нет примерно у каждого восьмого лота.

#### Таймер и быстрый контакт

- Таймер — ПЛАШКА во всю ширину низа снимка, а не угловой ярлык: угловых на фото уже два
  (класс кузова слева, номер лота справа). Градиент, а не сплошная заливка — снизу у
  снимков площадки бывает и светлый пол павильона, и тёмная тень.

  сервер и клиент считают время в разные моменты, и тикающее значение в первом рендере
  разошлось бы с разметкой. Интервал ОДИН на компонент и снимается при размонтировании —
  на странице их 24.
- `tabular-nums` стоит в самом компоненте: у пропорционального шрифта «1» уже «8», и
  строка дёргала бы соседей раз в секунду.
- ⚠️ Кнопка контакта на карточке стоит ВНЕ ссылки на снимок: фото и заголовок обёрнуты в
  `<Link>`, а `<a>` внутри `<a>` браузер чинит по-своему, разрывая внешнюю ссылку.

- Ведёт в WhatsApp с готовым текстом, а не открывает форму: `ContactFormModal` —
  клиентский компонент с i18next, и на 24 карточках это 24 модалки в дереве ради одного

- ⚠️ В сообщении НАШ адрес лота, а не `source_url` витрины. Иначе мы сами присылаем

  же механизм, что у карточки товара. Голый `/[lang]/parts` высаживал на первую страницу
  без фильтров.

#### Кнопка «в корзину» — ПЕРЕКЛЮЧАТЕЛЬ во всех трёх местах (23.08.2026)

Повторный клик убирает товар из корзины. Раньше стоял глухой `if (inCart) return;` (сетка,
`ProductCard`), зелёная плашка вместо кнопки (`QuickViewModal`) и `disabled` (карточка
товара, `ProductDetailClient`) — добавить можно было, убрать нельзя.

- ⚠️ **Локальных флагов «добавлено» быть не должно.** Во всех трёх местах жил свой
  `cartAdded` с таймером на 2–2.5 секунды, дублировавший реактивный `inCart` из стора
  (`useCartProductIds` слушает событие синхронизации и обновляется сразу после записи).
  С переключателем такой флаг переживает удаление и показывает галочку у товара, которого в
  корзине уже нет. Заодно с ним ушёл захардкоженный русский «✓ Добавлено» во всех локалях.
- `inCart` и `onRemoveFromCart` у `ProductCard` — ОБЯЗАТЕЛЬНЫЕ пропсы: карточку нельзя
  подключить в новом месте, забыв про корзину, и tsc это ловит.
- «Купить сейчас» на карточке товара при позиции, уже лежащей в корзине, открывает панель, а
  не добавляет её повторно: прежний код звал `addToCartCore()` ещё раз и молча удваивал
  количество по дороге на `/cart`.

#### Пустая выдача каталога = точка потери клиента, а не служебное состояние

Нулевой результат поиска раньше означал «Ничего не найдено» — клиент делал вывод, что
детали нет, и уходил. Теперь при `products.length === 0` рендерится `NoResultsBanner.tsx`
(`src/app/parts/sections/`): оффер «привезём под заказ» + три пути в личку — заявка через
тот же `OrderModal` (`source: parts_no_results`, артикул из поиска подставляется в
`partNumber`, лид уходит в Telegram через `/api/telegram`) и прямые ссылки
WhatsApp / Telegram с готовым текстом запроса.

- Инвариант: строка счётчика над сеткой при `total === 0` остаётся ПУСТОЙ — «ничего не
  найдено» больше нигде не дублируется. Не возвращать `t("parts.catalog.noResults")` в
  results bar.
- Ключи баннера — `parts.catalog.miss.*` во всех четырёх локалях. Ключи `noResults` /
  `noResultsHint` остались в JSON для других мест — их наличие не значит, что баннер их
  использует.
- События `search_no_results` (с `search_term`), `no_results_request`,
  `no_results_messenger` — это метрика спроса на то, чего нет в базе; ей меряется, что
  закупать. Не переименовывать без причины.

#### Поиск — отправка ЯВНАЯ, и URL там пишется мимо роутера

Строка поиска на `/[lang]/parts` (`SearchBar` в `PartsCatalogClient.tsx` — тот инпут, что
внутри `#catalog`, не пилюля в Hero) отправляет запрос только по кнопке «Найти», по Enter,
по крестику очистки и по событию `parts:hero-search` (там пользователь уже нажал поиск,
второго клика не просим). Дебаунса нет вообще; не возвращать
([постмортем](docs/postmortems.md)).

Три вещи, которые в коде не видны и которые легко сломать обратно:

- `q` пишется через `window.history.replaceState`, а НЕ `router.push`. Серверный рендер
  `/[lang]/parts` от `searchParams` не зависит (их читает только `generateMetadata` ради
  noindex на отфильтрованных URL), а товары приходят отдельным клиентским fetch'ем в
  `/api/parts/products`. Значит `router.push` здесь — чистая переплата. Фильтры, сортировка
  и пагинация НАМЕРЕННО остались на `router.push`: там URL — источник правды для выборки, и
  через него же работают back/forward. Отсюда параметр `updateParams(updates, { replace })`.
- `updateParams` строит параметры из `window.location.search`, а не из `useSearchParams()`.
  После `replaceState` хук обновляется не синхронно, и следующий клик по фильтру уносил бы
  `q` из адреса.
- Состояние ввода живёт ВНУТРИ `SearchBar` (memo), наружу уходит только отправленное
  значение. В корневом компоненте оно перерисовывало бы на каждую букву 24 карточки,
  сайдбар с фасетными счётчиками и облако категорий.
- `updateFilters` всегда снимает `page`. Любой новый эффект, дёргающий `updateFilters`,
  обязан пропускать первый прогон — иначе заход на `/ru/parts?page=5` перекинет сам себя на
  первую страницу.

#### Кеширование — три независимых рубильника, и выключенного хватает одного

Разобрано 29.09.2026, когда выяснилось, что за полтора месяца охват в Google упал с 4345
URL до 1097. Каталог не кешировался ВООБЩЕ: на каждой странице сайта стояло
`Cache-Control: private, no-store`, а даты последнего обхода живых страниц были 6 июня,
29 июня, 28 июля. Обход 50 тысяч страниц был для Google слишком дорог.

Рубильника три, и раньше все три стояли в положении «выключено».

**1. `cookies()` в КОРНЕВОМ layout делает динамическим ВСЁ дерево приложения.**
Он читался ради двух вещей — `<html lang>` и флага админа для счётчиков. Из-за этих двух
строк 48 тысяч карточек запчастей рендерились заново на каждый запрос.

⚠️ Отсюда ТРИ корневых layout через route groups, и это не украшение:
`(site)/[lang]/layout.tsx` берёт язык из `params`, `(root)` обслуживает `/` и
`/blog/[slug]`, `(admin)` — служебную часть со счётчиками, выключенными пропом. Общая
оболочка `<html>/<body>` — `src/app/RootShell.tsx`, метаданные — `src/app/rootMetadata.ts`;
держать три копии этого объекта значит однажды их рассинхронить.

Побочно это починило настоящий баг: `<html lang>` брался из cookie, поэтому посетитель с
`kmotors-lang=ru`, открывший `/en`, получал `lang="ru"`.

**2. Отсутствие `generateStaticParams` ОТКЛЮЧАЕТ ISR, а не только сборку страниц.**
⚠️ Это главная ловушка, и она стоила полутора месяцев. Без экспорта Next считает маршрут
полностью динамическим: он не попадает в `dynamicRoutes` манифеста, и `revalidate`
становится ДЕКОРАТИВНЫМ — кешировать отрендеренное некому. Лечится ПУСТЫМ массивом:
страниц на сборке не прибавляется (152 до и после), а ISR включается.

**3. `Set-Cookie` на ответе делает его приватным для CDN.** `kmotors-lang` и
`x-user-country` ставились на КАЖДЫЙ ответ. Для Googlebot это било сильнее всего: cookie
он не хранит, поэтому условие «её ещё нет» срабатывало каждый раз. Теперь боту не ставим
вовсе, живому — только когда значение изменилось.

#### Что кешировать НЕЛЬЗЯ, и почему

- `[lang]/page.tsx` и `[lang]/models/[slug]` читают `x-user-country` серверно. Закешируем —
  HTML корейского посетителя уедет всем остальным, и каталог авто спрячется у тех, у кого
  не должен.
- `[lang]/catalog/*` и `CarsRow` — живые данные Encar плюс та же cookie.
- ⚠️ `[lang]/parts/category/[slug]` и `[lang]/fitment/[brand]/[slug]` кешировать
  НЕВОЗМОЖНО, и `generateStaticParams` им добавлять бессмысленно: они читают
  `searchParams` ради пагинации `?page=N`, а это выводит маршрут из статического рендера
  ЦЕЛИКОМ — частично закешировать первую страницу Next не умеет. Проверено: с пустым
  экспортом маршрут попадал в `dynamicRoutes`, но ответ всё равно шёл с
  `private, no-store`, то есть экспорт создавал ВИДИМОСТЬ кеша. Чтобы закешировать,
  пагинацию пришлось бы унести в путь — это смена адресов и SEO-риск, не стоящий 142
  категорий и 627 страниц совместимости.

Текущие `revalidate`: `/[lang]/parts` 3600, `/[lang]/parts/[slug]` 86400,
`/[lang]/parts/category/[slug]` 3600, `/[lang]/fitment/[brand]/[slug]` 86400. У последних
двух он декоративен по причине выше.

TTL внутренних `unstable_cache` подчинены `revalidate` маршрута: если сегмент не
перерендеривается, эти TTL некому опросить.

#### Как проверять кеш — только этими двумя способами

Пометка `ƒ Dynamic` в выводе сборки и заголовок `Cache-Control: private` — ЛОЖНЫЕ следы
([постмортем](docs/postmortems.md)). Надёжны два:

```
node -e 'const m=require("./.next/prerender-manifest.json"); console.log(Object.keys(m.dynamicRoutes))'
curl -sI <url> | grep -i x-nextjs-cache      # MISS на первый заход, HIT на второй
```

Замер 29.09.2026 до/после: `prerender routes` 9 → 152, `dynamicRoutes` 0 → 2, карточка
товара `private, no-store` → `s-maxage=3600, stale-while-revalidate` с `HIT` на повторе.

Инвариант про цену и `revalidate ≤ 86400` — в «Жёстких правилах».

### Отслеживание посылок Korea Post EMS (19.08.2026)

Вход: `/[lang]/tracking`, из шапки — выпадашка на пункте «Запчасти», плюс ссылка в футере.
Механизм в `src/lib/emsTracking.ts`, ручка `/api/ems/track`, интерфейс
`src/app/tracking/TrackingClient.tsx`. Номер вводит клиент руками, история номеров живёт в
localStorage (`kaxis:ems-history`) и подставляется чипсами — своей таблицы у посылок нет.

Публичного API у Korea Post нет: шлём POST формой их же страницы на
`trace.epost.go.kr/xtts/servlet/kpl.tts.common.svl.SttSVL` с тремя полями, из HTML нужны
две таблицы по атрибуту `summary`.

- ⚠️ **Путь ручки `/api/ems/track`, а НЕ `/api/track`** — по второму адресу сидит приёмник
  first-party аналитики, который зовёт `middleware.ts`.
- ⚠️ **Парсер СВОЙ, без cheerio, и это осознанно.** Обе таблицы плоские (проверено на живом
  ответе), а зависимость ради одной страницы тянется в standalone-образ и заставляет
  пересобирать лок — на нашей Docker-сборке это дороже написанного парсера. Появятся
  вложенные таблицы — ставить настоящий парсер, а не чинить регулярки.
- Модуль не бросает исключений НИКОГДА, и три исхода разведены полем `status`. Схлопывать
  их нельзя: `not_found` («Korea Post такого номера не знает») и `upstream_error` («Korea
  Post не ответил») значат для клиента прямо противоположное — то же правило, что у
  `fetchVehicleData`.
- Ручка публичная и ходит на ЧУЖОЙ сервер, поэтому закрыта с двух сторон: маска S10
  (`EMS_NUMBER_RE`) отсекает перебор до похода наружу, плюс 20 запросов в минуту с IP и
  минутный кеш на номер в памяти инстанса. Сбой апстрима НЕ кешируется — иначе кнопка
  «обновить» целую минуту возвращала бы старую ошибку вместо настоящей попытки.
- Кеш ОДИН, и он в памяти инстанса. Всё остальное намеренно сквозное: `cache: "no-store"`
  на походе в Korea Post, `dynamic = "force-dynamic"` и `Cache-Control: no-store` на
  маршруте (без него браузер отдавал бы свою копию и кнопка «Обновить» была бы мертва),
  а сама страница и так рендерится динамически — корневой layout читает cookies, поэтому
  `revalidate` тут был бы декоративным ровно как у калькулятора. В localStorage лежат
  ТОЛЬКО номера, не результаты.
- ⚠️ **Строка «Проверено N назад» существует из-за этого кеша, а не для красоты.** В первую
  минуту «Обновить» молча возвращает копию из памяти, экран не меняется — и на посылке, где
  статус стоит сутками, кнопка выглядит сломанной. Убирать строку, не тронув кеш, нельзя.
- ⚠️ **Ворота индексации ОДНИ на всё — `TRACKING_INDEXED_LANGS` (ru + en).** Один и тот же
  список гасит индексацию в `generateMetadata` и убирает URL из `sitemap-main.xml`. ka/ar
  показывают английский текст через `fallbackLng` у i18next (переводов туда не делали,
  решение владельца 19.08.2026) — страница работает, но в индексе она была бы дубликатом
  `/en`. Тот же приём, что у калькулятора.
- ⚠️ **`?n=<номер>` тоже уходит в noindex.** Таких URL ровно столько, сколько посылок на
  свете; canonical при этом смотрит на чистую страницу.
- Незнакомый статус остаётся английской строкой из ответа Korea Post — это лучше пустоты.
  Словарь `tracking.status.*` заполнен только ru + en.
- ⚠️ **Цепь событий ОБРЫВАЕТСЯ после передачи экспедитору — это данные, а не баг парсера.**
  Проверено на реальной международной посылке `UE005194691KR` (19.08.2026): после
  «Handed over to Forwarder» Korea Post повторяет одну и ту же отметку `Loaded` сутками
  (шесть штук за пять дней) и НИЧЕГО больше не добавляет — ни прибытия в страну, ни
  таможни, ни вручения. Корейская версия страницы (`RetrieveEmsTraceCmd`) отдаёт форму
  поиска по внутренним отправлениям, то есть больше данных там нет.
  Решение владельца 19.08.2026: показываем ровно то, что даёт Korea Post — это официальные
  данные. Стадии «В стране получателя», «Таможня», «Вручено» у таких посылок так и остаются
  серыми, и это НЕ дефект интерфейса. Прогресс держит дата: `Loaded` идёт с новой датой
  каждый раз, поэтому дата последней отметки вынесена под заголовок статуса, а сноска
  внизу честно говорит, что дальше корейская почта не покажет ничего.
- ⚠️ **Повторяющиеся `Loaded` в ленте НЕ схлопывать** (решение владельца 19.08.2026):
  шесть одинаковых строк с разными датами — это и есть доказательство, что посылка едет.
- ⚠️ **«Страна назначения» и «индекс отделения» из колонки Details НЕ показываем и не
  парсим.** Korea Post пишет в них мусор: на обеих проверенных посылках в графе
  «Transit or Destination country» стояло `KOREA` (в том числе на международной), а в графе
  индекса — название отделения вместо цифр. «Страна назначения: Korea» на посылке в СНГ
  хуже, чем пустое место. Строки Details прячет `isKnownDetail` в интерфейсе.
- ⚠️ **`Handed over to Forwarder` разбирается ОТДЕЛЬНО от `Handed over to a transport
  company`**, и правило про экспедитора стоит в `STATUS_RULES` выше: события идут подряд, и
  общий перевод дал бы в ленте два неразличимых «Передана перевозчику».
- В кабинете (`account/OrdersTab.tsx`) трек-номер ведёт на эту страницу, а не на корейский
  epost, как раньше. Колонка `orders.tracking_url` осталась ручным переопределением для
  посылок НЕ через Korea Post — там отслеживать нечем, кроме сайта перевозчика.

### Блог — генерация статей (blog_topics → blog_posts)

`/api/blog-generate` (Gemini 2.5-flash напрямую, не через `llm.ts`): берёт из `blog_topics`
самую приоритетную тему со `status='pending'` → генерирует RU → переводит на EN (ko/ka/ar
не генерируем, их страницы noindex) → обложка с Pexels → вставка в `blog_posts`. Замер на
проде: ~45 сек на статью.

- Пост создаётся ЧЕРНОВИКОМ (`published: false`). На сайт он попадает только после кнопки в
  Telegram (callback `publish:` в telegram-webhook). Генерация ≠ публикация — «постов нет»
  может значить «черновики есть, их не одобрили».
- Квалити-гейт внутри ретрая: валидный JSON + минимум 700 слов + обязательная
  markdown-таблица. Три попытки.
- Провал НЕ сжигает тему: приоритет понижается на `PRIORITY_PENALTY`, `'failed'` ставится
  только когда приоритет исчерпан ([постмортем](docs/postmortems.md)).
- Пустой пул и остаток `<= LOW_POOL_THRESHOLD` шлют уведомление в Telegram.
- Статусы `blog_topics`: `pending` / `generated` / `skipped` / `failed`.

### Расписания — задачи Coolify, раннер ВНУТРИ контейнера

Расписания задаются в Coolify: Application → Scheduled Tasks. Там же видно, какие
задания активны и чем кончился каждый прогон — за этим их и уводят из crontab, где
список читается только по ssh.

Точка входа одна на все задания — `scripts/cron/run.mjs`. Задача в панели выглядит так:

| поле | значение |
|---|---|
| Name | `showcase` |
| Command | `node ./scripts/cron/run.mjs showcase` |
| Frequency | `0 */4 * * *` |

Таблица заданий с расписаниями лежит в самом раннере: `node scripts/cron/run.mjs --list`.
Разойдётся с панелью — правда за панелью, расписание задаёт она.

⚠️ **Задание выполняется ВНУТРИ контейнера приложения** (`docker exec`), а не на хосте.
Отсюда три вещи, каждая из которых ломает привычную строку crontab:

- ⚠️ **`curl` в образе НЕТ.** `node:20-alpine` несёт busybox, а curl ставится отдельным
  `apk add`, которого в Dockerfile нет. Команда с curl отработает ровно ноль раз и ляжет
  в историю как `not found` — ровно тот сценарий, на котором рассылка подписок простояла
  с первого дня.
- ⚠️ **Глобальный `fetch` тоже не годится.** У undici внутри Node `headersTimeout`
  300 000 мс, а заголовки ответа приходят, только когда маршрут ДОСЧИТАЛ: обход витрины
  аукционов идёт ~6 минут. То есть fetch отваливался бы по таймауту на работе, которая
  на сервере как раз успешно завершается, и задание краснело бы при живой синхронизации.
  У клиента `node:http` таймаута по умолчанию нет вовсе — поэтому он.
- Запрос идёт на `127.0.0.1:$PORT`, а не на публичный адрес: он не покидает контейнер,
  и ни DNS, ни TLS, ни Cloudflare с корейским правилом WAF на него не влияют.

⚠️ **Строка `COPY --from=builder /app/scripts/cron ./scripts/cron` в Dockerfile —
несущая.** Standalone-сборка тянет только то, что трассировка Next видит из импортов
приложения, а раннер приложение не импортирует — его зовёт планировщик снаружи. Уберут
строку — все задания начнут падать с `Cannot find module`.

Коды возврата раннера: 0 — успех, 1 — не достучались либо не 2xx, 2 — в ответе
`"ok":false`, 3 — ненулевой `unknownSource`. Код 2 существует потому, что эндпоинты
отвечают 200 и когда делать было нечего, и когда источник не отдал ни строки: без этого
в истории был бы ровный ряд зелёных галочек над мёртвой витриной.

Бэкап в Coolify не переносится: он вызывает скрипт на ХОСТЕ, вне репозитория и вне
контейнера приложения. Это единственное задание, которое действительно исполняет файл.

**Переносить оставшиеся по одному:** завести задачу в Coolify с командой
`node ./scripts/cron/run.mjs <аргумент>`, дождаться зелёного прогона, и только потом
снять строку из `crontab -e`. Пока оба планировщика работают параллельно, задание
отрабатывает дважды — для всех безопасно, кроме автопостинга: дедуп не даст запостить
ОДНУ И ТУ ЖЕ машину дважды, но частота постинга удвоится, пока не упрётся в дневной
лимит. Строку автопостинга снимать ДО первого прогона в Coolify, а не после.

#### Пока задания остаются в crontab

⚠️ **На VPS НЕТ рабочей копии репозитория.** Прод собирается Coolify в Docker, каталога
`/var/www/kmotors/` не существует. Поэтому каждая оставшаяся строка crontab — прямой
`curl` к эндпоинту, и никаких вызовов скриптов там быть не может.

Скрипты `scripts/*-cron.sh` живут в репозитории как документация и для ручного запуска с
локальной машины. На проде они НЕ исполняются, а строки из их шапок
(`/var/www/kmotors/scripts/...`) ставить в crontab нельзя: cron каждый раз пишет в лог
`not found`, задание не отрабатывает ни разу, и снаружи это выглядит как «функция не
работает», а не как ошибка конфигурации. Так рассылка подписок простояла с первого дня —
пока не выяснилось, что путь не существует (31.07.2026).

Не возвращать блок `crons` в `vercel.json` ([постмортем](docs/postmortems.md)).

Образец строки (методы разные, сверяться с таблицей — `-X POST` там, где POST):

```
*/5 * * * * curl -fsS --max-time 300 -H "x-poster-secret: $SECRET" https://www.kmotors.shop/api/subscriptions/run >> /var/log/subscriptions.log 2>&1
```

Правило проверки — одно на оба планировщика: после любой правки убедиться, что в логе
(или в истории прогонов Coolify) появилась строка с JSON-ответом, а не `not found` и не
пустота. Отсутствие сообщений от задания само по себе НЕ означает, что задание отработало
и ничего не нашло.

Секретов два, не больше. `POSTER_CRON_SECRET` (заголовок `x-poster-secret`) закрывает
`/api/poster/run`, `/api/poster/parts/run`, `/api/rss-sync`, `/api/blog-generate`,
`/api/subscriptions/run`, `/api/showcase/sync`, `/api/carnect/sync` и `/api/cars/sync`. `SEO_CRON_SECRET` (заголовок
`x-seo-secret`) закрывает SEO-пайплайн. `CRON_SECRET` больше не используется нигде — он
был задан только в README и ни разу в окружении.

### Сайтмапы — краул-бюджет делится между авто и запчастями, и это не поровну

Мастер-индекс `src/app/sitemap.xml/route.ts` собирает: `sitemap-main.xml` (статические
страницы × 4 языка + модельные + индексируемые категории запчастей), `sitemap-blog.xml`
(только ru+en, остальные языки noindex), `sitemap-fitment.xml` (поколения с
`parts_count >= 10`), затем `sitemap-parts/1..N` (по 1 000 товаров) и
`sitemap-catalog/1..N` (по 200 машин). `robots.ts` отдаёт Google ТОЛЬКО `sitemap.xml` —
дочерние файлы отдельно не подаются.

Соотношение сил: запчастей ~48 700 URL, машин 5 000. Запчасти вечные, машина одноразовая
(продалась → Encar 404 → noindex), поэтому у каталога авто `priority` 0.5 против 0.7 у
запчастей — это НЕ баг.

#### Сайтмап каталога идёт из `cars_seen`, а не из выдачи Encar (02.10.2026)

⚠️ **Это замена прежней offset-пагинации по живой выдаче, и возвращать её нельзя.**
Выдача Encar сортируется по `ModifiedDate`, то есть пересобирается при каждом
переподнятии объявления, — значит offset не адресовал НИЧЕГО: страница N через час
держала другие машины. Google не мог построить очередь обхода и не строил её.

Замер 02.10.2026, на котором это вскрылось: карточки авто за шесть недель потеряли 90%
показов (2559 URL в выдаче 13–19.08 → 253 к 30.09) при НЕИЗМЕННОЙ позиции, причём
11 из 14 топовых августовских карточек к тому дню были проданы (Encar 404 → noindex,
штатно), а 8 из 8 машин, взятых из ЖИВОГО `sitemap-catalog/1`, дали в URL Inspection
«URL неизвестен Google, обход НИ РАЗУ». Старые вымывались продажами, новые не заходили.

Что даёт своя таблица:

- Страница сайтмапа адресует машины НАШИМ ключом. Набор меняется только когда машина
  реально появилась или продалась, а не каждый час от бессмысленности offset'а.
- ⚠️ **`<lastmod>` ВЕРНУЛСЯ, и это не откат прежнего решения.** Убирали его потому, что
  единственной доступной датой был `ModifiedDate` Encar — дата переподнятия объявления, и
  отдавать её значило каждый час объявлять изменённым весь каталог. Теперь дата своя,
  `first_seen_at`, и она у машины НЕ МЕНЯЕТСЯ: `saveCarSnapshots` не кладёт эту колонку в
  payload, поэтому upsert её не перезаписывает. Переобход на ровном месте не просится.
  `changefreq` по-прежнему нет — Google его игнорирует.
- Проданные выпадают по `sold_at`, который ставит рендер карточки на 404 от Encar. Google
  обходит адрес → получает 404 → машина помечена → в следующей сборке её нет. Петля
  замыкается без единого лишнего запроса к Encar. Отсутствие машины в листинге продажей НЕ
  считается: листинг — скользящее окно по верхушке 155-тысячного пула.
- ⚠️ **Сортировка — `first_seen_at DESC` плюс `encar_id` ВТОРЫМ ключом.** Батч-upsert
  проставляет один и тот же `first_seen_at` сотням строк разом, то есть ключ неуникален, и
  без второго машины пропадали бы между страницами (общее правило `.range()` выше).
- `CATALOG_SITEMAP_PAGE_SIZE` и `CATALOG_SITEMAP_MAX` живут в `src/lib/carsSeen.ts`, и
  оттуда их берут ОБА маршрута. Прежние `CATALOG_MAX_CARS` / `MAX_OFFSET` были двумя
  копиями одного числа в двух файлах с припиской «меняешь здесь — меняй и там»;
  рассинхронить их больше нечем.
- Число файлов каталога в индексе считается по РЕАЛЬНОМУ содержимому таблицы, а не по
  потолку: сослаться на 25 файлов при трёх машинах значит отдать 22 пустых ответа, которые
  Google исправно скачает. Supabase не ответил → берётся потолок, потому что индекс без
  каталога читается как «этих URL у нас больше нет».

⚠️ **`LIMIT` у задания `cars` — регулятор СРОКА ЖИЗНИ адреса в сайтмапе, а не «сколько
успеем».** Потолок 5 000, сортировка от новых к старым, значит каждая добавленная машина
вытесняет самую старую. При 500 в сутки адрес лежит в сайтмапе около десяти дней — этого
обходу хватает. Залив по 2 000 четыре раза в сутки сменил бы весь набор за день, и мы
вернулись бы ровно к той болезни, от которой ушли: URL исчезает раньше, чем до него
доходит краулер. Потолок 5 000 против 48 700 запчастей — это +6% к набору, краул-бюджету
безразлично.

Замер качества набора на 02.10.2026: из 40 машин, взятых с первой и последней страницы
нового сайтмапа, живы на Encar 39. То есть Google получает живые карточки, а не склад
проданных.

**Дублей в сайтмапе каталога больше НЕТ — не искать и не чинить.** Прежний документ
описывал их как терпимые: один файл содержал ~200 URL на ~180 уникальных Id, и между
файлами дубли тоже были, потому что страницы offset'а перекрывались на движущейся ленте
Encar. Замер на проде 02.10.2026 после перехода: внутри файла 200 URL на 200 уникальных
Id, пересечение между первой и последней страницей — ноль. Это следствие пагинации по
собственному ключу, а не отдельная починка.

### Калькулятор растаможки — семь стран в одном интерфейсе

Вход: `/[lang]/calculator` (Россия по умолчанию) и `/[lang]/calculator/[country]`.
Ядра в `src/lib/customs/core/countries/`, курсы в `src/lib/customs/fx/`, интерфейс в
`src/components/Customs/`, тесты в `tests/customs/`. Словарь — неймспейс `customs`,
подключается opt-in, как `cars`.

Сведён 11.08.2026 из двух: прежнего RU/KZ/UZ на сайте и отдельного проекта
`customs_calculators` (GE/AM/KG/AL). Тот проект **заморожен**, источник правды здесь.

- **У каждой страны своё ядро, таблицы ставок между странами НЕ шарятся.** Армения и
  Кыргызстан считают по одному своду ЕТТ, и таблицы у них совпадают до цента — они всё
  равно продублированы. Законы меняются несинхронно; общий модуль тут не экономия, а
  связанность.
- **Ядро — чистая функция.** Без DOM, сети и `new Date()`: расчётный год и месяц приходят
  во входном объекте. Округление, которое является частью расчёта, живёт в ядре;
  форматирование — в интерфейсе.
- ⚠️ **Вход ядра БЕЗ поля в форме обязан быть в `RUNTIME_INPUT_IDS`** (`core/registry.ts`).
  Тип `RuntimeInputs` заставляет `CalculatorPanel` подать каждый ключ списка, тест в
  `registry.spec.ts` — не завести новый мимо списка. Связка не бюрократия: `currentMonth`
  не подавался вовсе, возраст был `NaN`, сравнения с `NaN` ложны, и калькулятор России
  считал ЛЮБУЮ машину как «старше 5 лет» при зелёных тестах ядра
  ([постмортем](docs/postmortems.md)).
- **Ядро не возвращает текст.** `Line.label`, `note`, `Flag.text`, `subtitle`, `stampLabel`
  — это `I18nText { key, params }`; строку собирает интерфейс через `resolveText`. Параметр
  сам может быть `I18nText` (возрастной бракет внутри формулы акциза), обход рекурсивный.
  `meta` осталась под МАШИННЫЕ значения — коды бракетов, промежуточные суммы.
- ⚠️ **Опечатка в ключе — не ошибка компиляции, а сырой ключ на странице у клиента.**
  Ловится `tests/customs/i18n.spec.ts`: он гоняет ядра по сетке параметров, собирает все
  ключи и проверяет, что каждый есть в словаре и получил свои `{{параметры}}`.
- **Табы — это `<Link>`, а не `useState`.** У каждой страны свой URL и свои метаданные;
  ощущение таба даёт клиентская навигация Next. Семантика навигационная (`aria-current`).
- ⚠️ **Хранилище общих параметров формы лежит в `calculator/layout.tsx`, а не внутри
  `[country]`.** Layout ВНУТРИ динамического сегмента перемонтируется при смене параметра —
  Next держит разные значения разными узлами кэша, — и введённое обнулялось на каждом
  переключении таба. Проверено маркером монтирования.
- **`generateStaticParams` здесь бесполезен.** Корневой layout читает куки, всё дерево под
  `[lang]` рендерится динамически. Список `lang × country` дал пустой prerender-manifest.
  На рантайм это не влияет — про два ложных следа при диагностике кеша см. постмортемы.
- `revalidate = 21600` на обоих маршрутах: страница рендерит курс, правило «не выше 86400»
  из «Жёстких правил» действует.
- Курсы тянет `fx/getRates` (open.er-api → ЦБ РФ → вшитый снимок), 10 валют. **У ЦБ РФ
  рубль — база, отдельной записи в `Valute` нет**, поэтому он берётся особым случаем; без
  этого RUB молча уходил бы в снимок. Падение на снимок логируется `console.error` с
  перечнем валют — это требование правила про `?? FALLBACK`.
- Токены `--color-calc-*` и `--font-calc-*` в `globals.css`, отдельно от `axis.*` и
  `--pn-*`. Шрифты Space Grotesk и JetBrains Mono подключены в сегментном layout
  калькулятора, а не в корневом.
- **Узбекистан сверен 11.08.2026 по текстам актов**, как и Казахстан: приложение №1
  к ПП-3818 (пошлина), ПКМ №347 (утильсбор), ПКМ №55 (таможенный сбор), ст. 246–248
  НК РУз (НДС). 17 кейсов в `tests/customs/golden/uzbekistan.golden.json`, ожидания
  посчитаны рукой, курс круглый (12 000 сум/$). Прежнее ядро было перенесено из
  калькулятора сайта дословно и разошлось с законом почти по каждой строке.
- ⚠️ **В Узбекистане ставку решает СТАТУС машины, а не её возраст.** Тариф делит
  8703 на «новые» (коды `xx 10`) и «бывшие в эксплуатации» (`xx 90`), и это про факт
  регистрации, а не про год выпуска. Корейская машина с аукциона зарегистрирована,
  значит она б/у при любом пробеге — 40% + $3,0/см³ вместо 15% + доплата. Поэтому в
  форме отдельное поле `condition` со значением `used` по умолчанию; выводить статус
  из года выпуска НЕЛЬЗЯ, это занижает растаможку больше чем вдвое.
- **Ставка б/у — одна на всё: 40% + $3,0/см³.** Ни объём, ни бензин/дизель, ни
  возраст её не дробят. В номенклатуре у б/у есть подсубпозиции «более 7 лет»,
  «5–7 лет» и «прочие», и по ним легко решить, что ставка тоже возрастная — в
  приложении к ПП-3818 у всех кодов `8703 xx 90` одна строка.
- ⚠️ **Гибрид (8703 40/50 и 60/70) считается по ДВУМ разным правилам, и это не
  ошибка.** НОВЫЙ платит голый процент без доплаты за см³ — 15% до года, 30% старше;
  так прямо в приложении к ПП-3818. С ПРОБЕГОМ доплата появляется, и ставка
  становится возрастной: до трёх лет 30% + доплата по объёму (шкала 0,4–1,25 $/см³),
  старше трёх лет 40% + 3,0 $/см³, то есть ровно как у бензина (решение владельца
  12.08.2026 по его источникам). Не «выравнивать» эти две ветки между собой: у
  нового гибрида отсутствие доплаты — это то, что подтверждено актом.
- ⚠️ **Электромобилю в Узбекистане утильсбор НЕ обнуляется.** Пошлина 8703 80 —
  0% без оговорки о возрасте, а вот утильсбор с 01.05.2025 подняли до 120 БРВ
  (до 3 лет) и 210 БРВ (старше). Прежнее ядро ставило ноль. Строка ПКМ №347 звучит
  «имеющие электродвигатель, ЗА ИСКЛЮЧЕНИЕМ транспортных средств гибридной
  мощности» — гибриды считаются по объёмной шкале, а не по этой.
- **Таможенная стоимость в РУз = цена сделки ПЛЮС доставка до границы** (решение
  владельца 11.08.2026). Поле `freightUsd` со значением 2 250 $ по умолчанию,
  редактируемое, всегда в долларах независимо от валюты сделки. Это НЕ строка чека:
  фрахт задаёт базу сразу трёх адвалорных платежей — ступени таможенного сбора,
  процентной части пошлины и НДС. На типовом профиле он добавляет к итогу ~15 млн сум.
  Доставку отдельной строкой в чеке НЕ показываем — она только база.
- **Госпошлины СБДД (бывшее ГАИ) — отдельная строка В ИТОГЕ**, не `extra` (решение
  владельца 11.08.2026): 13,04 БРВ = 5 372 480 сум (регистрация 6,84 + техпаспорт 0,7
  + номера 5,5). У чистых электромобилей 7,7 БРВ; гибриды платят как бензиновые.

### Аналитика GA4 — четыре воронки (05.10.2026)

Цель владельца: видеть, на каком шаге человек уходит, и понять, почему машины смотрят,

- ⚠️ **`section` у каждого события ставит `trackEvent` САМ** по адресу (`sectionFromPath`):

  за просмотр (`trackOnce`, ключ — адрес с query).
- ⚠️ **Имена параметров заведены в GA4 как специальные параметры** — переименовать

- ⚠️ **`aria-label` на голом `<div>` не работает — нужна роль.** У `<div>` неявная роль
  `generic`, а на ней спецификация ARIA запрещает `aria-label`, и скринридер его молча
  игнорирует. В футере так вышли безымянными карточки платёжных систем: иконки внутри
  помечены `aria-hidden`, подпись висела на контейнере — и не читалась ни та, ни другая
  (найдено аудитом Lighthouse 23.08.2026). Лечится ролью, а не снятием атрибута:
  `PayCard` получил `role="img"`, то есть стал изображением с текстовой альтернативой.
  Тот же приём годится любому блоку из декоративной графики с подписью; для модалок
  правильная роль — `dialog` (так и сделано в `ReviewsPopup`).
- `src/lib/matryoshka.ts` + `src/lib/ems-rates.ts` — упаковка посылок EMS в коробки Korea
  Post, чтобы минимизировать оплачиваемый вес.
- `src/lib/supabase/client.ts` vs `server.ts` — браузерный и серверный клиенты
  (`@supabase/ssr`).
- Админка (`src/app/admin/`) — авторизация отдельная от витрины: одна переменная
  `ADMIN_PASSWORD` + cookie `admin_session`, проверяется в `middleware.ts`.
- `design-reference/` — отдельный проект на Vite, визуальный референс; к рантайму `src/`
  отношения не имеет.
- `src/components/ui/dialog.tsx` — потребитель у примитива ОДИН, модалка заявки
  (`Header/ContactFormModal.tsx`), так что правки в нём больше ничего не задевают.
  Заливка карточная (`--axis-charcoal`), а не `--background`: на чёрной странице модалка
  обязана быть светлее фона. Рамки нет НАМЕРЕННО — 1px по токену `--border` читался как
  белый кант, край держит тень плюс внутренний хайлайт в 4%.
- ⚠️ Ссылка на Instagram лежит в ТРЁХ местах (`Header/Header.tsx`, `Footer/Footer.tsx`,
  `ui/SocialRow.tsx`) и везде без хвоста `igsh` / `igsi` / `utm_source=qr` — это
  одноразовый токен шаринга из QR-кода, постоянной ссылке на сайте он не нужен.
  Меняется профиль — править все три.

## Внешние системы

### Encar API — замеры (29.07.2026, curl с сервера)

- Листинг: 70–90 мс, до 200 записей за запрос. Троттлинга на 25 запросах подряд нет,
  user-agent не обязателен.
- Прокси на Render режет выдачу до 20 записей независимо от запрошенного лимита — отсюда
  10 запросов бэкфилла напрямую против 100 через прокси.
- Проверять конкретную машину — `api.encar.com/v1/readside/vehicle/{id}` (200 живая /
  404 проданная). Фильтр `Id.<id>.` в поисковом запросе отдаёт HTTP 404 (проверено в обеих
  кодировках скобок); именно он стоит в `useFavoritesSync.ts`, из-за чего алерты по цене в
  избранном не работали ни разу ([постмортем](docs/postmortems.md)).
- Глубокие offset'ы молча клампятся примерно после ~50k, а сортировку стабилизировать
  нечем — детали и направление решения в
  [docs/open-questions.md](docs/open-questions.md).

### Google Search Console

- API доступен из скриптов через сервисный аккаунт: переменные `GSC_SA_JSON` (ключ
  сервисного аккаунта, JSON одной строкой) + `GSC_SITE_URL=https://www.kmotors.shop/`.
  Хелпер: `src/lib/gsc.ts` (JWT → REST `searchAnalytics/query`), `google-auth-library`
  установлена. Ручной экспорт лежит в
  `./https___www.kmotors.shop_-Performance-on-Search-2026-07-12/`, но это снимок — за
  актуальными цифрами ходить в API.
- ⚠️ Клики и показы из Кореи (`country = "kor"`) — это собственный трафик владельца, а НЕ
  реальные пользователи. ВСЕГДА исключать Корею из любого SEO-анализа
  (`dimensionFilterGroups` country notEquals `"kor"`). Корея давала ~43% кликов в
  трёхмесячном окне, так что нефильтрованные тоталы — и особенно видимая позиция и показы
  калькулятора — сильно искажены.

### Корея закрыта в ТРИ независимых слоя

Изменение одного слоя не влияет на другие.

- **Слой 3, запрет на origin (05.10.2026)** — `isKoreaBlocked` в `src/middleware.ts`:
  на каноническом хосте при `cf-ipcountry = KR` отдаётся 403 на каталог Encar, аукцион,
  избранное, сравнение (`KR_BLOCKED_PAGE`) и на ВСЕ API с данными машин
  (`KR_BLOCKED_API`: recommended, vehicle, carnect, cars, kcar, showcase). Решение
  владельца: «всё с аукционов и Encar и вниз по дереву закрываем полностью» — WAF
  закрывал только часть путей, и страница лота аукциона из Кореи открывалась.
  ⚠️ Новый маршрут или API с данными машин — добавить в эти регулярки. ⚠️ Ответ
  `private, no-store`: зависит от страны, в общий кеш попадать не должен. Служебный
  хост и кроны (127.0.0.1, без `cf-ipcountry`) не затрагиваются.

- **Слой 1, Cloudflare WAF** (вне репозитория, отсюда его не прочитать и не изменить):
  кастомное правило блокирует запросы из Кореи на эдже. Исключение — Skip-правило с
  бо́льшим приоритетом по cookie, выражение `http.cookie contains "my_secret_key=<value>"`.
  ЗНАЧЕНИЕ НАМЕРЕННО НЕ ЛЕЖИТ В ЭТОМ ФАЙЛЕ: репозиторий на GitHub ПУБЛИЧНЫЙ (проверено
  через `gh repo view` — visibility PUBLIC), поэтому всё закоммиченное здесь навсегда
  доступно всему миру, включая историю git и любой форк. Хранить в `.env` / менеджере
  паролей. Чтобы использовать — поставить cookie один раз в браузере для kmotors.shop либо
  передать `--cookie "my_secret_key=<value>"` в curl; код приложения его не читает.
- ⚠️ **Область блока WAF — ТОЛЬКО каталог авто, не весь сайт** (замерено 29.07.2026 с
  корейского IP): 403 отдают `/{lang}/catalog` и `/{lang}/catalog/{id}`; `/{lang}`,
  `/{lang}/parts`, `/{lang}/blog`, `/{lang}/calculator`, `/sitemap.xml`, `/robots.txt` и
  `/api/*` открыты и проверяются без всякой cookie. Пришедший из Кореи 403 на карточке авто
  — это работающее правило, а не сломанный прод; не искать причину в приложении.
- **Слой 2, скрытие ссылок в приложении:** `CATALOG_BLOCKED_COUNTRIES = ["KR"]` в
  `src/hooks/useCountry.ts`. `middleware.ts` копирует `cf-ipcountry` в читаемую браузером
  cookie `x-user-country` (24ч), и её сравнивают с `"KR"` в ВОСЬМИ местах: `useCountry()`
  на клиенте (Header, Footer, Home/Main, Home/NavCards, Home/PopularModels, CTA в статье
  блога) плюс две серверные страницы, читающие cookie напрямую через `cookies()` —
  `[lang]/page.tsx` и `[lang]/models/[slug]/page.tsx`. Только авто — запчасти остаются
  видимыми.
- Слой 2 косметический, это НЕ средство контроля доступа: он только прячет ссылки.
  `/[lang]/catalog` отвечает 200 кому угодно, кто дошёл до origin, а cookie тривиально
  правится в devtools. Не считать это контролем доступа и не «чинить» избыточность между
  слоями.
- Следствие для исключений: Skip-cookie Cloudflare проводит через эдж, но ссылки в навигации
  всё равно останутся скрытыми — слой 2 смотрит на `x-user-country` и про обход ничего не
  знает. Реальный вайтлист = править оба места. Именно поэтому владельческий вход сделан
  не cookie, а отдельным хостом — см. ниже.

#### Владельческий вход — служебный хост, а не cookie (18.08.2026)

Обход через `my_secret_key` остаётся рабочим, но рутинный доступ владельца из Кореи идёт
через отдельный поддомен на том же origin, с Cloudflare Access поверх. Korea-правило WAF
сужено до `http.host eq "www.kmotors.shop"`, поэтому на служебном хосте каталог просто
работает — с любого устройства и любой сети, без куки и без привязки к IP.

- ⚠️ **Cookie как владельческий вход провалилась по механике браузеров, а не по замыслу.**
  Поставленная руками в DevTools cookie получается сессионной (поле Expires пустое) и
  умирает при закрытии браузера; записанная через `document.cookie` в Safari живёт максимум
  7 дней из-за ITP независимо от указанного срока. Не предлагать «просто поставить cookie
  подольше» как решение.
- ⚠️ **IP-вайтлист рассматривался и отвергнут: он неприменим к мобильному интернету.** У
  сотовых операторов CGNAT — адрес меняется при каждом переподключении и одновременно
  принадлежит тысячам абонентов, так что разрешить его значит открыть каталог посторонним.
  Домашний IP (`14.5.115.104` в `EXCLUDED_IPS`) закрывает только сценарий «владелец дома».
- ⚠️ **«Секретный поддомен» сам по себе не секретен.** Имя хоста попадает в публичные
  Certificate Transparency логи в момент выпуска сертификата и находится через crt.sh за
  минуту. Access на этом хосте — не перестраховка, а единственное, что его закрывает.
- Access повешен на ПОДДОМЕН, а не на `www/catalog`, намеренно: WAF отрабатывает раньше
  Access, поэтому путь через www потребовал бы снять боевое Korea-правило, и ошибка в
  политике увела бы весь каталог за логин для живых посетителей и Googlebot. На поддомене
  поведение www не меняется вообще.
- Всё, что не `CANONICAL_HOST` (из `NEXT_PUBLIC_SITE_URL`), middleware считает служебным
  входом и делает с ним три вещи: `X-Robots-Tag: noindex, nofollow` поверх ЛЮБОГО ответа,
  подмену `/robots.txt` на `Disallow: /` и обнуление cookie `x-user-country` — последнее и
  есть снятие слоя 2 разом во всех восьми местах. Заходы через служебный хост не попадают
  в аналитику (`shouldTrack`).
- ⚠️ **Заголовок ставится в обёртке над всей middleware, а не в её ветках.** Точек выхода
  восемь (410, редиректы ko/parts/lang, админка, `isExcluded`, основной путь) — в любой
  новой про заголовок забудут, и служебный хост уйдёт в индекс полной копией сайта.
- Индексации мешают ТРИ независимые вещи, и убирать их по одной нельзя: Access (краулер не
  доходит до страницы), заголовок с robots.txt и абсолютные canonical на www в самих
  страницах. Заголовок в HTML не запекается, поэтому общий кеш Next между хостами его не
  разносит, а canonical в кеше и так всегда указывает на www.
- Апекс `kmotors.shop` без `www` под это правило тоже попадёт — если он когда-нибудь начнёт
  доезжать до origin вместо редиректа на эдже, страницы отдадутся с `noindex`.

Кнопка «Поделиться» в карточке авто (`Catalog/CarDetail/ShareCar.tsx`, стоит в шапке из
`[lang]/catalog/[id]/page.tsx`) — второй потребитель того же понятия «служебный хост». На
www она одна и отдаёт текущий адрес; на служебном хосте их две, клиентская собирает
www-ссылку, менеджерская — ссылку на служебный хост.

- ⚠️ **Менеджерская ссылка бесполезна тому, чьей почты нет в политике Access.** Получатель
  упрётся в тот же экран входа и не пройдёт — ошибки при этом не будет, просто логин по
  кругу. Даёшь ссылку новому человеку — сперва добавь его почту в политику (бесплатный
  тариф держит 50).
- ⚠️ **Хост читается в `useEffect`, а не при рендере.** На сервере `window` нет, и первая
  клиентская отрисовка обязана совпасть с серверной, иначе React ругается на рассинхрон
  гидрации. Поэтому в SSR-HTML всегда ровно ОДНА кнопка, публичная, и это не баг: вторая
  появляется после монтирования. Проверять компонент через `curl` бессмысленно.
- `CANONICAL_HOST` вычисляется из `NEXT_PUBLIC_SITE_URL` тем же выражением, что в
  `middleware.ts`. Меняешь определение служебного хоста — меняй в обоих местах.

Три грабли, на которые ушёл час при первой настройке 18.08.2026. В коде их не видно ни
одной — все три в чужих интерфейсах.

- ⚠️ **`Direction` в Coolify обязан стоять `Allow www & non-www.`** Значение по умолчанию
  было `Redirect to www.`, и Coolify вешает это правило на ПРИЛОЖЕНИЕ целиком, а не на
  конкретный домен: любой хост без `www` получает его приклеенным, то есть служебный вход
  уезжал на `www.office.kmotors.shop` — имя, которого в DNS нет, `DNS_PROBE_FINISHED_NXDOMAIN`.
  Настройка была вдобавок бесполезна: апекс редиректится на www на эдже Cloudflare, до
  origin не доходя (замерено, в ответе `server: cloudflare`). Добавляя приложению новый
  домен, проверять этот выпадающий список.
- ⚠️ **Служебный хост нельзя назвать `www.office.kmotors.shop`, чтобы «узаконить» редирект.**
  Универсальный сертификат Cloudflare покрывает `*.kmotors.shop` — ОДИН уровень. На
  двухуровневом имени будет ошибка сертификата.
- ⚠️ **Редирект такого рода curl'ом не диагностируется.** Неавторизованный запрос Access
  обрывает первым (302 на логин), поэтому до редиректа дело не доходит и в выводе curl его
  нет НИКОГДА — виден он только в браузере, уже после входа. Плюс Chrome кеширует 301
  бессрочно: получив его однажды, он уводит на битый хост и после починки сервера. Проверять
  с открытым DevTools и галочкой «отключить кеш», иначе чинится уже исправное.
- One-time PIN включать не нужно, он метод входа по умолчанию, когда провайдеров нет
  (`Zero Trust → Integrations → Identity providers`, путь в новой навигации; `Settings →
  Authentication` из старой документации не существует). Экран
  `dash.cloudflare.com/oauth/consent-form` — это НЕ логин Access, а выдача прав OAuth на
  аккаунт Cloudflare; правильный экран живёт на `<team>.cloudflareaccess.com` и просит
  только почту.
- Каталог авто закрыт для Кореи намеренно (безопасность + SEO): `/ko/*` 301-редиректится в
  `/en/*` (`middleware.ts`), чтобы SEO-вес легаси корейских URL консолидировался на `/en`.
  Не помечать как баг ни редирект ko→en, ни отсутствие `ko` в hreflang, ни остаточные
  клики по `/ko/` в GSC.
